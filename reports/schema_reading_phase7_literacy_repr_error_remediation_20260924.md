## 0. 최우선 확인 — "연구용 환경" 전제 재검증 (경고)

**결론: literacy.db는 research/production이 분리돼 있지 않다. 단 하나의 로컬 DB만
존재한다.** 이번 세션에서 직접 재확인했다(1번 지시가 요구한 대로, phase4의 결론을
믿지 않고 다시 확인):

- `app/literacy/db.py`를 직접 읽음: `DB_PATH = REPO_ROOT / "data" / "literacy.db"`
  하드코딩, `APP_ENV` 등 환경변수 분기 코드가 **전혀 없다**. `vocabulary_quiz`
  쪽(`VOCABULARY_QUIZ_DB_PATH` 환경변수로 서버 research DB와 분리)과 근본적으로
  다른 구조다.
- 서버(`aprolabs` SSH)에 별도 `literacy.db`가 있는지도 확인 시도했으나, 이번 세션의
  literacy 관련 작업은 전부 로컬 `data/literacy.db` 하나만으로 완결되고 서버 쪽
  literacy.db 존재 여부와 무관하게 로컬 파일이 유일한 "진짜" 데이터임이 코드로
  이미 확정돼 있어(하드코딩 경로), 추가 SSH 조사 없이도 이 결론은 바뀌지 않는다.

**함의**: "연구용에서만 작업하면 안전하다"는 안전판이 literacy 모듈에는 구조적으로
없다. 이 로컬 DB에 대한 모든 쓰기는 곧 유일한 실사용 DB에 대한 쓰기다. 그래서
이번 세션은 다음을 평소보다 엄격하게 적용했다: (a) 새 컬럼/테이블 발명 금지를
문자 그대로 지킴, (b) 쓰기 작업(2번) 전 SQLite Backup API 백업 + 무결성 검증,
(c) 적용 후 체크섬 대조 및 재실행 멱등성 확인, (d) 게이트 실패 시 즉시 중단
원칙(이번 세션은 실제로 한 번도 실패하지 않았다 - 9절 참고).

## 1. `유용하다`류 오류의 실제 노출 여부 — 코드 추적 + 실제 재현

### 1-1. id 표기 정정 (재검증 중 발견)

phase6은 `유용하다`를 "literacy.db id=565"로 적었으나, 이번 세션이 literacy.db를
직접 재조회한 결과 **id=565는 전혀 다른 표제어("고사리 같은 손")**였다. 실제
`유용하다`(momo-textbook 소스, 잘못된 뜻)는 **literacy.db id=2891**이다.
`565`는 momo_book.db `vocabulary.id`(대표로 선정된 L2 원본 행, definition=NULL)를
가리키는 값이었던 것으로 확인된다 — phase6 원문이 두 DB의 id 체계를 섞어 쓴
표기 오류였다(재조사 금지 지시가 있었지만, 이번 지시가 "실제 쿼리로 재현"을
명시적으로 요구했기 때문에 그 과정에서 자연스럽게 드러난 사실이며, phase6의
**실질적 결론**(krdict 동음이의 오매칭)은 그대로 유효하다 — 아래 1-4절에서 krdict
원본까지 재조회해 재확인함).

### 1-2. 코드 경로 추적

`app/literacy/*`를 전수 확인한 결과:

- `app/routers/literacy_admin.py` (prefix `/literacy`): `/terms`(전체 조회),
  `/review/*`(문항·뜻풀이·레벨 검수 화면) 전부 **관리자용 화면**이다. 라우터
  주석에 "전부 관리자용 - 전역 인증 미들웨어가 그대로 적용된다"고 명시돼 있고,
  실제로 라우트 함수 자체에는 `is_admin` 체크가 없다 — `app/main.py`의
  전역 `auth_middleware`가 **로그인 여부만** 확인한다(역할 구분 없음).
- `app/routers/literacy_api.py` (prefix `/api/literacy`): 파일 자체 docstring에
  "문해력 DB 학생용 라우터 (동작 확인용 최소 엔드포인트만)"이라고 명시돼 있고,
  실제 코드는 `GET /api/literacy/health -> {"status":"ok"}` **단 하나뿐**이다.
  `docs/literacy/01-스키마.md`도 "추후 momoai.kr에서 호출할 때 이 prefix만 인증
  화이트리스트에 넣을 예정 - 지금은 화이트리스트를 수정하지 않는다"고 명시한다.
  → **학생에게 데이터를 반환하는 엔드포인트 자체가 아직 코드로 존재하지 않는다.**
- `app/main.py`의 `auth_middleware`: `public_paths = {"/login", "/logout"}` +
  `/static`, `/uploads`, `/api/external` 만 인증 예외. `/literacy/*`, `/api/literacy/*`
  모두 예외에 없다 — 로그인하지 않으면 전부 `/login`으로 302 리디렉션된다.
- `app/models/user.py`(aprolabs.db 자체 계정 테이블)에는 **역할(role) 필드 자체가
  없다** — `email`, `hashed_pw`, `is_admin`(불리언)뿐이다. "학생" 역할이라는 개념이
  aprolabs 코드베이스에 **존재하지 않는다**(이는 vocabulary_quiz 모듈의 별도 인증
  체계 `app/vocabulary_quiz/auth.py`와는 완전히 다른 시스템이다).
- `app/routers/auth.py`: 로그인(`/login`) 라우트만 있고 **회원가입/계정생성 라우트가
  없다**. 로컬 `aprolabs.db`를 직접 조회한 결과 계정은 `admin@aprolabs.co.kr`
  **단 1개뿐**이다(앱 기동 시 `_create_admin()`이 하드코딩 생성).

### 1-3. 실제 재현(코드 추적에 그치지 않고 실제 요청을 보냄)

로컬에서 `uvicorn app.main:app`을 기동해 실제 HTTP 요청으로 재현했다(비밀번호나
세션 토큰은 어디에도 노출/출력하지 않기 위해, 두 단계로 나눠 확인했다 — ①
미인증 상태는 실제 서버에 curl로 직접 요청, ②"로그인된 사용자가 있다고 가정했을
때 무엇이 보이는가"는 `app.auth.get_current_user_id`를 테스트 목적으로만
스텁 처리한 `starlette.testclient.TestClient`로 확인 — 실제 크리덴셜은 전혀
생성·출력하지 않음).

```
① 미인증(실제 서버, curl)
GET /literacy/terms        -> 302, Location: /login?next=/literacy/terms
GET /api/literacy/health   -> 302, Location: /login?next=/api/literacy/health

② 인증됨(TestClient, 로그인 스텁)
GET /literacy/terms?q=유용하다
  -> 200, 응답 HTML 테이블에 실제로 다음 행이 렌더링됨:
     헤드워드=유용하다 / 카테고리=어휘 / 정의="남의 것이나 이미 용도가 정해져
     있는 것을 다른 데에 쓰다." / 레벨=0 / 출처=momo-textbook / 검수상태=검수전

GET /literacy/review/definition?id=2891
  -> 200, 이 화면은 "뜻풀이 작성" 전용 화면이라 기존 definition 값을 렌더링하지
     않음(빈 textarea) - 이 화면에서는 오류 텍스트가 노출되지 않는다.

라우트 전수 목록 확인 결과: /literacy/*, /api/literacy/* 전체를 통틀어 실제로
term.definition을 HTML로 렌더링하는 곳은 /literacy/terms 하나뿐이다.
```

**결론**: `유용하다`(id=2891)를 포함한 26건의 잘못된/손상된 정의는 **오직
`/literacy/terms` 관리자 브라우즈 화면**에서만 실제로 노출된다. 그리고 이 화면에
도달하려면 **로그인**이 필요한데, aprolabs 전체를 통틀어 로그인 가능한 계정은
개발자 본인의 admin 계정 1개뿐이며 "학생" 역할/계정 개념 자체가 이 코드베이스에
없다. `/api/literacy/*`(향후 momoai.kr 학생용으로 예정된 경로)는 헬스체크
하나뿐이라 **실제 데이터를 반환하는 학생용 경로가 아직 존재하지 않는다.**

**→ "학생에게 노출 가능한 상태"라는 조건 자체가 이번 세션 기준으로 충족되지
않는다.** 이는 phase4가 vocabulary_quiz 쪽에서 보인 "student_exposure=0"과는
별개의, literacy 모듈 자체의 독립적인 확인 결과다(지시대로 그 플래그를 가정하지
않고 별도로 조사함).

### 1-4. 26건 전부 같은 경로에서 조회되는지 확인

26건(3절 판정표) 전부를 `/literacy/terms?q=<headword>`로 순회 조회한 결과, **26건
전부 같은 관리자 브라우즈 화면에서 같은 방식으로 노출됨**을 확인했다(코드 경로가
`Term.headword.contains(q)` 하나뿐이라 카테고리·출처 무관하게 전부 같은 로직을 탐).

### 1-5. 차단 실행 여부 — "차단 불가"로 명시하고 중단

두 가지를 확인했다:

1. **노출 전제 불충족** (1-3절) — 학생에게 실제로 노출되는 경로가 없다.
2. **설령 전제가 충족되더라도, 기존 필드만으로는 실질적 차단이 불가능하다** —
   `app/literacy/models.py`의 `Term.review_status`(검수전/검수완료/보류/제외)가
   유일하게 존재하는 상태 필드이지만, `/literacy/terms`(정의 전체가 노출되는
   **유일한** 화면)의 쿼리(`terms_browse` 함수, `literacy_admin.py` L502-534)는
   `review_status`를 **필터 조건으로 전혀 쓰지 않는다** — 컬럼 값을 화면에 표시만
   할 뿐, 숨기는 로직이 없다. `is_active`/`is_published`류 필드는 `Term` 모델에
   **아예 존재하지 않는다**. 즉 `review_status`를 `보류`로 바꿔도 `/literacy/terms`
   화면에서는 여전히 그대로 노출된다 — 이 화면을 실제로 가리려면 라우터 코드에
   새 필터 조건을 추가해야 하는데, 이는 "기존 필드의 새로운 사용처를 만드는 것"
   이라 이번 세션의 "함부로 새 메커니즘을 만들지 말 것" 지시에 저촉될 소지가 있다
   판단해 실행하지 않았다.

**결론: 이번 세션은 literacy.db에 대해 1번 항목의 쓰기(차단)를 실행하지 않았다.**
근거: (a) 노출 전제 자체가 충족되지 않음(1-3절), (b) 설령 예방적으로 처리하려
해도 기존 필드에는 화면단 차단 효과가 없어 "차단"이라는 이름에 걸맞은 실질적
효과를 낼 수 없음(껍데기만 바꾸는 것은 오히려 잘못된 안전감을 줄 위험). 지시문의
표현을 그대로 빌리면 **"차단 불가, 사용자 판단 필요"** — 다만 이는 "메커니즘이
없어서"가 아니라 "메커니즘은 있지만 이번 노출 지점(terms 브라우즈)에 연결돼 있지
않아서"이므로, 사용자가 원한다면 다음 두 가지 중 하나를 다음 세션에서 선택할 수
있다:
   - (A) `terms_browse` 쿼리에 `review_status != '보류'` 필터를 추가하는 라우터
     코드 변경(기존 컬럼 재사용, 새 컬럼 없음) + 26건을 `보류`로 설정, 또는
   - (B) `/api/literacy/*`가 실제로 데이터를 반환하게 되는 시점(momoai.kr 연동)에
     맞춰 그 신규 엔드포인트 설계 단계에서부터 `review_status` 필터를 처음부터
     넣는 것(현재는 관리자 화면만 있으니 시급하지 않음).

DB는 건드리지 않았으므로 백업도 만들지 않았다(1번 항목에 한해 — 2번 항목은
실제로 썼으므로 아래 2절에서 별도로 백업했다).

## 3. momo_book.db 대표선정 오류 26건 — 개별 판정표 (제안만, DB 미변경)

### 3-1. 방법

phase6의 방법론(정제 → 컬럼의심 제외 → 표제어 그룹화 → `(grade_level, vocab_id)`
오름차순 대표선정 → 손상 신호 스캔)을 `scripts/literacy/scan_momo_book_repr_errors_26.py`
로 재구현해 재현했다. 이번 세션은 여기서 한 걸음 더 나아가, **krdict 원본 XML을
직접 재조회**해 "동음이의어의 다른 뜻이 채택됐는지"를 실측했다(단순 텍스트 비교가
아니라 `pick_krdict_match`가 실제로 어떤 후보 풀에서 어떤 항목을 골랐는지까지
재현).

### 3-2. 판정 결과 요약

| 판정 | 건수 | 의미 |
|---|---:|---|
| **REPLACE_CANDIDATE**(교체후보, 근거 확인됨) | **6** | 유용하다·관대하다·모락모락·선구자(동음이의/다의어 오선택 확인) + 혼비백산·독불장군(구두점 손상) |

산출물: `reports/literacy_repr_errors_26_verdict_20260924.csv`,
`reports/literacy_repr_errors_26_verdict_20260924.jsonl` (표제어, momo_book.db
원본 위치(vocab_id/level), literacy.db 현재 채택 정의, 다른 후보 정의(들),
판정, 근거, dry-run 제안 값 전부 포함).

### 3-3. 핵심 발견 — krdict 동음이의 오매칭이 유용하다 1건이 아니라 2건 더 있었다

krdict raw XML을 직접 재조회한 결과, **관대하다도 유용하다와 동일한 버그
패턴**임을 이번 세션에서 처음 확인했다: krdict에 `관대하다` 동음이의 2건이
존재하고(동사 '친절하고 정성스럽게 대하다.' / 형용사 '마음이 넓고 이해심이
많다.'), `note` 컬럼에 실제로 `krdict 동음이의 2건 중 1번 채택`이 기록돼 있다 —
현재 literacy.db에는 틀린 동사 뜻이 저장돼 있고, 형용사 뜻('너그럽다')이 올바른
뜻이다.

추가로 **모락모락**·**선구자**는 동음이의(서로 다른 표제어)가 아니라 **krdict
단일 항목 안의 여러 뜻(sense) 중 첫 번째가 아닌 다른 뜻**이 교재 맥락과 일치하는
사례임을 확인했다 — `pick_krdict_match`가 `entry.definitions[0]`(첫 번째 뜻)을
기계적으로 채택하는 동일한 구조적 원인이 "동음이의 표제어"뿐 아니라 "다의어 단일
표제어"에도 똑같이 적용됨을 보여준다. 즉 이 버그의 실제 영향 범위는 phase6이 특정한
"`pick_krdict_match`의 첫 번째 동음이의 채택"보다 넓다 — **"definitions 리스트에서
항상 인덱스 0만 쓰는 모든 지점"**이 잠재적 위험 지점이다(`import_textbook_vocab.py`
L221, `import_sajaseongeo.py`류와 별개로 어휘 수집 전반에 해당).

### 3-4. 또 다른 발견 — phase6이 "정보 손실"로 분류한 2건은 재검증 결과 오류가 아니었다

`허사`·`자초지종`을 krdict과 대조한 결과, 현재 literacy.db 값이 **krdict의 유일한
정의와 정확히 일치**했다(자초지종은 다른 후보들과도 사실상 동일 문자열). 오히려
momo_book.db의 "정보량 많아 보이는" 후보 쪽(`허사` L4, id=784)이 krdict 어디에도
대응하는 뜻이 없어 momo_book.db 자체의 표제어-정의 매칭 오류로 의심된다(교재DB는
이번 세션에서도 손대지 않았다 - 기록만). 이는 "대표가 짧다 = 정보 손실"이라는
phase6의 휴리스틱이 항상 옳지는 않다는 것을 보여주는 반례이며, 이번 세션이 요구한
"표제어만 보고 판단하지 말고 실제 의미 대조 근거를 확인하라"는 지시가 실제로
결과를 뒤집은 사례다.

## 6. 최종 요약 (호출한 에이전트용)

1. **literacy.db 분리 여부**: 분리 없음, 단일 로컬 DB(`data/literacy.db`) 하드코딩
   확인(0절). "연구용 안전판" 전제가 이 모듈에는 없다.
2. **1번(유용하다류 노출)**: 학생에게 실제로 노출되는 경로가 **없다** — 코드
   추적 + 실제 HTTP 재현(로그인 없이 302 차단, 로그인 가능한 계정은 admin
   1개뿐, "학생" 역할 개념 자체가 코드베이스에 없음, `/api/literacy/*`는
   헬스체크뿐)으로 확인. 26건 전부 동일 경로(`/literacy/terms` 관리자 화면)에서만
   노출. **차단 실행 안 함** — 노출 전제 불충족 + 기존 `review_status` 필드가
   해당 화면에서 필터로 전혀 쓰이지 않아 실질적 차단 효과가 없음을 확인했기
   때문("차단 불가, 사용자 판단 필요"로 명시). DB 쓰기 없음.
3. **2번(파서 10건 적용)**: **적용 완료**. 게이트 전부 PASS(하드가드/백업 무결성/
   값 일치 10-10/체크섬 불변/integrity_check ok/fk_violations 0/멱등성 확인),
   롤백 0회. 백업 SHA-256 `47303bce...`.
4. **3번(26건 판정표)**: REPLACE_CANDIDATE 6건(유용하다·관대하다·모락모락·선구자
   [동음이의/다의어 오매칭] + 혼비백산·독불장군[구두점손상]) / HOLD 1건(궁색하다) /
   NO_ISSUE 19건(재검증 결과 오류 아님으로 판명). **DB는 건드리지 않음**, 전부
   dry-run 제안.
5. **4번(AI 레벨 정책)**: 우선순위 62(정책충돌)/10(교차상충+자기모순)/159(제외,
   그중 10건은 콘텐츠정책·2건은 사실검증형으로 분리) 재확인. GROUNDED=0이 구조적
   필연임을 grade_level 전량 NULL로 재확인. 자동 대조 확장 설계: 정밀학년
   자기모순 재검사(대상 206건, 미실행) + 표제어 정규화 확장매칭(대상 2,634건,
   미실행) 제시, 외부 코퍼스 도입은 범위 밖으로 명시. **DB 변경 없음.**
6. **만든 파일**: 5절 목록 참고(스크립트 5개, 데이터/판정표 4개, 백업 1개, 본
   보고서 1개).
7. **가장 중요한 리스크**:
   - (a) literacy.db는 research/production 분리가 없어 앞으로의 모든 쓰기가
     즉시 실사용 데이터에 반영된다 — 이번처럼 매 단계 백업·게이트를 계속
     의무화해야 한다.
   - (b) `pick_krdict_match`의 "definitions[0] 고정 채택" 버그가 유용하다
     1건이 아니라 **관대하다·모락모락·선구자까지 최소 4건**으로 확인됐고, 이는
     "동음이의 채택" 범위를 넘어 "다의어 단일 표제어의 sense 선택"까지 구조적으로
     걸려 있는 문제라 momo-textbook 821건 전체에 더 있을 가능성이 있다(이번
     세션은 26건 대표선정-오류 후보군 안에서만 확인했다 - 전수 재검사는 범위 밖).

     지금은 admin 혼자 쓰는 도구라 위험이 낮지만, 향후 `/api/literacy/*`가
     실제로 학생용 데이터를 반환하게 될 때 이 필터 부재를 그대로 이식하면 안 된다.

     점은 사용자 결정이 필요한 채로 남아 있다(4-3절).
