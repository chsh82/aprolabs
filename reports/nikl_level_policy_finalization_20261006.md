## 1. 실험 종료 선언 — 규칙 분류기·Gemini v1~v3 기록 보존

아래 4개 보고서를 **최종 실험 기록**으로 보존하고, 이 프로젝트의 L3/L4 자동
분류 실험 라인을 종료한다. 추가 Gemini 호출·v4 설계·새 100건 검수 배치는
만들지 않는다(이번 작업 전체에서 API 호출 0건).

| 세대 | forced 정확도 | L4 재현율 | 결론 |
|---|---:|---:|---|
| 규칙 기반(뜻풀이 길이 임계값) | 58.3% | - | 다수결(60.0%)보다 낮아 화면 노출도 권장 안 함 — `nikl_grade5_batch1_analysis_and_classifier_20261002.md` |
| Gemini v1(최소정보) | 73.7%(200건 재집계) | 25.3%(20/79) | 2차 독립평가서 L4 재현율 28.2%로 하락 확인, 자동 제안 부적합 — `nikl_grade5_gemini_classifier_experiment_20261003.md`, `nikl_grade5_batch2_independent_evaluation_20261004.md` |

24~28% 구간에 머물렀다. 입력을 바꾸거나(최소정보→교과서/한자어 교정→사용자
빈도 신호) 프롬프트 문구를 아무리 다시 써도 이 천장을 넘지 못했다 — 문제가
"프롬프트가 부족하다"가 아니라 "모델에게 실사용 빈도 같은 근거 데이터 자체를
주지 못한다"는 구조적 한계로 보인다. 이 판단은 v3 보고서 6절에서 이미
내렸고, 이번에 뒤집히지 않았다(추가 실험을 하지 않았으므로 뒤집을 근거도
만들지 않았다).

## 2. 공식 5등급 전체 목록(17,000건) — 기본 추천 범위 + 200건 사람 판정 연결

## 5. 연구 화면 최소 변경 제안 (설계만, 코드 미적용)

**현황**: 공식 레벨과 현재 레벨을 그나마 같이 보여주는 화면은 tier1 상세
(`/vocab-official-grade-review/{content_id}`) 하나뿐인데, 공식 추천값이
`diff_reason`이라는 자유서술 문장 안에만 섞여 있고 "현재 DB 레벨"만 별도
블록으로 깔끔히 분리돼 있다. 목록 화면(`official_grade_review_index.html`)은
공식 레벨 필드를 아예 따로 보여주지 않는다. 다른 화면(검수 화면들)은 공식
레벨을 전혀 노출하지 않는다.

**제안(최소 변경, 코드는 이번에 작성하지 않음)**:
1. tier1 상세·목록 템플릿에 `공식기반추천범위`(L0~L2 또는 "경계(L3~L4)")를
   `diff_reason` 문장에서 분리해 **읽기 전용 배지 하나로 단독 표시**한다 —
   서비스 계층이 이미 `VocabularyOfficialGradeReference.proposed_base_level`을
   들고 있으므로 템플릿만 수정하면 된다(새 쿼리·새 테이블 불필요).
2. 그 옆에 "현재 출제 레벨"(`vocabulary_content_levels.vocab_level` +
   `level_status`)을 **지금처럼 그대로** 별도 블록에 둔다 — 두 값을 합치거나
   하나로 뭉개지 않는다(공식 근거·사람 판정을 서로 덮어쓰지 않는다는 2·3절
   원칙을 화면에서도 유지).
3. 3절의 5,950건 통합표를 그대로 CSV 다운로드/관리자 읽기 전용 목록으로
   노출하면(새 화면 하나, 쓰기 기능 없음) "공식 레벨+현재 레벨"을 한눈에 보고
   싶을 때 tier1처럼 1건씩 클릭하지 않아도 된다 — 이것도 신규 쓰기 기능은
   전혀 필요 없다(기존 조회 쿼리를 그대로 라우트 하나로 노출하는 정도).
4. **모델 제안(v1/v2/v3)은 이번에도 어떤 화면에도 추가하지 않는다** —
   2절의 "비노출" 컬럼은 분석용으로만 남긴다.

**경계 어휘를 단일 출제 레벨 기능에서 다루는 방법(임의로 L3/L4에 넣지
않음)**: 현재 `vocabulary_content_levels.vocab_level`은 NOT NULL
INTEGER(CHECK 0~6)라 "경계"를 표현할 null이 없고, 소비 코드
(`multiformat.py`의 `_select_level_candidates()`)는 `boundary_flag`/
`level_status`를 전혀 보지 않고 `vocab_level` 정수만 바로 읽는다 — 즉
**오늘 기준으로 "경계" 표시는 광고용일 뿐 실제로 단일 레벨 기능에서 강제되지
않는다**는 걸 이번에 확인했다(사실 확인, 추측 아님). 이번 작업 범위의 49건
"공식5등급_미검수"·향후 16,800건 신규 후보가 실제 content로 들어오는 시점에
이 문제가 실제로 발생할 것이므로, 제안은:

- 신규 콘텐츠를 만들 때 "경계(L3~L4)" 추천값을 가진 항목은
  `vocab_level`에 **임의의 정수를 넣지 않고, `public_ready=0`·
  `student_exposure` 상태로 생성을 보류**한다(사람이 L3/L4 중 하나를
  확정하기 전에는 애초에 단일 레벨 선택 풀에 들어갈 콘텐츠 자체를 만들지
  않는 것 — 지금의 "advisory 플래그" 방식보다 안전하다).
- 이미 존재하는 콘텐츠(이번 49건 같은 경우)에 대해서는, `_select_level_
  candidates()`가 `level_status='REVIEW_BOUNDARY'`인 행을 **단일 레벨 선택
  풀에서 제외**하도록 조건을 추가해야 한다(현재는 advisory, 강제 아님) —
  이건 기존 동작을 바꾸는 코드 수정이라 이번엔 적용하지 않고 제안만
  남긴다(사용자 승인 후 별도 턴에서 진행).
