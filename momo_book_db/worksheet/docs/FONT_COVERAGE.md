# 폰트 커버리지 (docs/FONT_COVERAGE.md)

문제 1(폰트 서브셋 범위 부족) 조치 내역. 기존 방식은 신화의숲 학습지 1건에
실제로 등장한 554자만 담은 서브셋이었는데, 이 렌더러가 앞으로 220종의 서로
다른 도서를 조판하므로 서브셋 밖 글자가 조용히 다른 폰트로 대체 렌더링되는
결함을 막기 위해 전면 재작업했다.

## 1. DB 전수 스캔

`momo_book_db/momo_book.db`에서 실제 학습지 본문에 흘러 들어가는 4개 컬럼을
전수 스캔했다 (`scripts/check-font-coverage.py`가 매 실행마다 다시 수행):

- `discussion_qa.question_text`
- `discussion_qa.excerpt_text`
- `vocabulary.definition`
- `documents.background_text`

결과: 총 **649,082자**(공백 포함) 중 고유 문자 **1,867종**.

## 2. 선택한 커버리지 전략

`text=` 파라미터로 글자를 제한하는 대신, Google Fonts CSS2 API의 **기본(무제한)
패밀리 요청**을 그대로 받았다. 이 방식은 한국어 로케일용으로 이미 다음을
기본 포함한다 (실측으로 확인):

- 한글 완성형 **11,172자 전체**(U+AC00–D7A3) — 100% 커버
- 기본 라틴/숫자/문장부호(ASCII 0x20–0x7E) — 100% 커버
- 한글 자모(U+3131–318E) — 100% 커버
- Noto Serif KR / Noto Sans KR 기본 상용 한자 세트

웨이트는 가이드 1.3 그대로: Gowun Batang 400/700, Noto Serif KR 400/600/700,
Noto Sans KR 400/500/700. Gowun Batang은 표지 전용(`.cover__title` 등)이라
본문 커버리지 검증 대상에서는 제외했다(DB 텍스트가 그 폰트로 렌더링되는
경로가 없음).

한 패밀리+웨이트당 유니코드 레인지로 쪼개진 다수의 woff2 파일이 생성된다
(패밀리·웨이트별 95~124개). 브라우저는 페이지에 실제로 쓰인 글자가 속한
레인지의 파일만 내려받으므로, 로컬에 934개 파일이 있어도 실제 로드량은
한 문서에서 쓰는 글자 수만큼만 든다 — "파일 크기가 커지는 건 괜찮다"는
지시에 따라 총량보다 회귀 방지를 우선했다.

## 3. 한자 커버리지 확인

DB에서 실제로 쓰인 CJK 한자는 **181자**. 기본 패밀리 요청이 이 중
**177자를 커버**했다. 커버 안 된 4자(为 U+4E3A, 么 U+4E48, 独 U+72EC,
関 U+95A2)는 전부 `L3-Q1-W01` 한 문서에서만 나왔고, 이 문서는 아래 4절에서
설명하는 폰트/인코딩 손상 문서로 확인되어 **의도적으로 제외**했다(정상
한자가 아니라 깨진 추출 결과이므로 커버해도 의미가 없음).

## 4. 기호류 보충 서브셋

전수 스캔 결과 기본 패밀리 요청 밖에 있던 문자 중, 본문 안에 실제로 인라인으로
등장하는 타이포그래피 기호 10종을 확인했다 — 예: `｢임진록｣`(낫표),
`제기차기 ∙ ∙ 팽이치기`(가운뎃점 구분자), `➀병원에 다녀 온 뒤`(원문자 마커),
`✎ 디킨스의 묘비에는`(연필 기호), `♫시의출발은`(음표) 등. 이 기호들이 본문
서체와 다른 대체 폰트로 렌더링되면 문장 중간에 이질감이 생기므로, Google
Fonts CSS2 `text=` 파라미터로 정확히 이 10자만 담은 보충 subset을
Noto Serif KR(400/600/700)·Noto Sans KR(400/500/700) 각각에 추가로 받아
`fonts.css` 끝에 `@font-face` 6개 블록으로 덧붙였다(`*-supplement.woff2`,
패밀리당 약 1.1KB — 사전에 Google API 응답으로 이 10자 모두 두 폰트에
실제 글리프가 있음을 확인한 뒤 받음):

```
∙ ｢ ｣ ➀ ➁ ➜ ✎ ▪ ⦁ ♫
```

이모지(🎬 U+1F3AC, 💡 U+1F4A1 — `L8-Q2-W10`)는 의도적으로 서브셋에 넣지
않았다. 컬러 이모지 글리프는 애초에 Noto Serif/Sans KR 같은 일반 텍스트
웹폰트에 없고, 브라우저가 지정한 font-family와 무관하게 항상 OS 표준
이모지 폰트로 렌더링하는 게 표준 동작이라 — 어차피 대체되며, 그 대체가
플랫폼 표준이라 "조용히 다른 걸로 바뀌는 결함"에 해당하지 않는다.

## 5. 검증 결과 (scripts/check-font-coverage.py)

`python scripts/check-font-coverage.py`로 DB 전수 스캔 → `fonts.css`의
`unicode-range` 파싱 → Noto Serif KR ∪ Noto Sans KR 합집합 기준 커버리지
대조를 매번 다시 계산한다. 현재 결과: **미커버 58자**, 전부 아래 6-문서의
손상된 데이터이거나(56자) 의도적으로 제외한 이모지(2자)다. 정상 문서에서
나온 미커버 문자는 0건.

## 6. 새로 발견한 폰트/인코딩 손상 문서 (범위 밖이지만 보고)

이번 전수 스캔과 문맥 대조 과정에서 폰트 서브셋과 무관하게 **DB 자체의
추출 품질 문제**로 보이는 문서를 추가로 발견했다. 원래 이번 작업 범위는
아니지만("범위 밖: DB 스키마 변경" — 데이터 자체를 고치라는 뜻은 아니었고,
발견된 사실은 보고 대상이라 판단해 기록한다.

기존에 알려진 손상 문서(`docs/DB_REPORT.md`): `L3-Q4-W06`, `L8-Q4-W07`,
`L9-Q4-W01`, `L9-Q4-W02`.

이번에 새로 확인한 것:

| doc_id | 증상 | 예시 |
|---|---|---|
| `L9-Q4-W01` | 다국 문자(아랍/히브리/아르메니아/조지아/데바나가리/벵골/칸나다 등) 51종 난입 | 이미 `docs/DB_REPORT.md`에 등록된 손상 문서와 동일 계열 |
| `L3-Q1-W01` | 한글 문장에 일본어/중국어 문자 혼입 | `メリト는貧しく孤独な少女でした。それなのに요나스 페테르가...` |
| `L2-Q4-W07`, `L4-Q1-W04` | `L3-Q1-W01`과 같은 계열(다국 문자 혼입) | 이번 회차 조사 초반에 발견(문항 텍스트 검토 중) |
| `L6-Q1-W07` | **단일 글자 치환** — 정상 단어 자리에 한글 자모 확장-B(U+D7B0, 미할당에 가까운 옛한글 자모)가 들어감 | `맥베스는 ힰ 없이 고개만 끄덕일 뿐이었어요` |
| `L2-Q2-W10` | 위와 동일 패턴, 다른 코드포인트(U+D7AC) | `지금 내가 힘든 것보다 훨씬 더 힬 수 있어` |
| `L7-Q1-W09` | 유니코드 비문자(U+FFFF, 정의상 유효한 문자가 될 수 없는 코드포인트) 삽입 | `<보기> ▪￿시 해설 다음은...` |

`L6-Q1-W07`·`L2-Q2-W10`·`L7-Q1-W09`는 앞의 다국-문자-난입형과 달리 **글자
하나만 깨져 있어** 눈으로 훑어봐서는 거의 티가 안 나는 유형이다(문장은
자연스럽게 이어지고 이상한 글자 하나만 섞여 있음). 전수 스캔 + 문맥 대조로만
잡혔다. 220종 도서를 렌더링하기 전에 추출 파이프라인 점검이 필요해 보이지만,
이건 폰트 문제가 아니라 데이터 추출 문제이므로 이 작업 범위 밖으로 두고
사실만 보고한다.

## 7. 최종 결과물

- 파일 수: 934(기본 무제한 패밀리 요청) + 6(기호 보충 서브셋) = **940개 woff2 + fonts.css**
- 총 용량: **약 21MB**
- 실제 로드량: 브라우저가 유니코드 레인지 단위로 지연 로딩하므로 한 문서당
  몇 개 파일만 받음(로컬 서빙이라 네트워크 비용 없음 — 사전 합의된 트레이드오프)
