# 포팅 노트 — 신화의숲 1차시 학습지 v2 → 정적 HTML/CSS

원본: `신화의숲 1차시 학습지 v2.dc.html` + `DESIGN_GUIDE.md` + `doc-page.js`/`support.js` (모두 `학습 교재 디자인 샘플.zip` 안에 있던 파일)

## 1. 가이드(DESIGN_GUIDE.md)와 샘플이 어긋나는 지점

지침에 따라 이런 경우 **샘플의 실제 렌더 결과를 정답으로 삼았다.**

### 1.1 페이지 수
- 가이드 3행: "기준 샘플: ... A4 10장"
- 실제 샘플(`신화의숲 1차시 학습지 v2.dc.html`)의 `<section class="page">` 개수: **11개** (표지 1 + 1단계 1 + 2단계 8 + 3단계 1)
- 가이드 4.2절의 산출 공식("표지 1 + 1단계 1 + 2단계 6~8 + 3단계 1 = 9~11장")과는 맞는데, 3행의 "10장"이라는 숫자 자체가 오타로 보임. → **11페이지가 맞다고 보고 그대로 포팅함.**

### 1.2 학년 톤의 "도장(stamp)" 크기·각도
- 가이드 1.4표: 초5~6 톤은 `2.05em / -2°`
- 실제 샘플의 도장 span(`min-width:1.9em;height:1.9em`, 회전 없음): **1.9em / 0°** — 회전이 전혀 없다.
- → `tone-elem56`에서는 **샘플 값(1.9em, 0°)을 그대로 씀.** 초3~4·중등 톤은 검증할 샘플이 없지만, 문제 2 조치로 가이드 표의 **비율/차이를 샘플 값에 그대로 이식**해 재계산했다(가이드 값을 그대로 쓰지 않음 — 아래 참고).

  | | 가이드 크기 | 가이드 각도 | → 샘플 기준 재계산 |
  |---|---|---|---|
  | 초3~4 | 2.15em | -3° | 크기: `1.9 × (2.15/2.05) = 1.99em` / 각도: `-3 + (0-(-2)) = -1°` |
  | 초5~6 | 2.05em | -2° | 샘플 실측값 그대로 `1.9em / 0°` |
  | 중등 | 1.95em | 0° | 크기: `1.9 × (1.95/2.05) = 1.81em` / 각도: `0 + (0-(-2)) = 2°` |

  크기는 **가이드 표의 초5~6 대비 비율**을 그대로 곱해서(예: 초3~4는 가이드에서도 초5~6보다 4.9% 크므로, 샘플 앵커에도 4.9% 크게), 각도는 가이드 세 톤이 등차수열(-3°, -2°, 0°가 아니라 실제로는 -3, -2, 0으로 톤마다 2°/1°씩 차이)로 짜여 있다고 보고 **가이드 elem56과 샘플 elem56의 차이(+2°)를 세 톤 전부에 동일하게 더하는 평행이동**을 택했다(초5~6만 회전이 없다는 샘플의 특징을 초3~4/중등에도 유지하려는 것 — 비율로 하면 회전 0°인 elem56을 기준으로 나눗셈이 성립하지 않아서 각도는 비율이 아니라 이동으로 처리함). 이렇게 나온 값이 `styles.css`의 `--stamp-size`/`--stamp-rotate` (초3~4: `1.99em/-1deg`, 중등: `1.81em/2deg`) — **여전히 미검증**(그 학년 실제 교재가 나오면 대조 필요)이지만, 적어도 "가이드 숫자를 그대로 베낀 값"이 아니라 "샘플이라는 검증된 앵커에서 가이드의 상대적 관계만 가져온 값"이라 근거가 더 명확하다.

### 1.3 학년 톤의 "본문/행간" 값 — 문제 2 조치로 실제 적용됨 (수정 이력)
처음 포팅 때는 아래처럼 만들었었다(지금은 아님 — 기록으로 남겨둠):
> 발췌문(`.excerpt`)·질문(`.q__text`)·캡션 등 모든 텍스트 요소가 자기만의 고정 rem 크기를 갖고 있어 톤과 무관했고, 톤에 따라 실제로 바뀌는 건 답란 줄 간격(`--ruleH`)뿐이었다. `--tone-body-size`/`--tone-line-height` 변수는 정의만 해두고 신규 블록 `.blk-fallback`에만 연결해 두었다.

이후 사용자가 이 상태를 지적함(★): 이건 단순 기록이 아니라 **톤 전환 기능 자체가 구현되지 않은 것**이고, `docs/CAPACITY.md`의 톤별 실측이 전부 같은 조건을 측정한 것이 되어 표 자체가 무효화될 수 있다는 지적이었다. 고치기 전에 먼저 확인한 결과, 실제로 수정 전 `docs/_measure_raw.json`에서 톤 3종의 안전 조합 수가 (11, 11, 11)로 완전히 동일했고 대표 `scrollHeight`도 사실상 같았다(1px 차이는 톤별로 이미 갈라져 있던 `--ruleH`가 답란 높이에 준 영향일 뿐) — **지적이 맞았다.**

**수정 내용**: 고정 rem 대신 톤 변수 기반 `calc()`로 바꿨다.
- 루트(`.worksheet`)의 `font-size`를 `calc(16px * var(--tone-scale, 1))`로 바꾸고, 본문 텍스트 요소들은 `px` 고정값 대신 `rem` 단위를 쓰게 해서 루트 크기 변화가 자동으로 전파되게 함.
- 본문 텍스트 요소(`.vocab-def`, `.ox-item__text`, `.excerpt`, `.q__text`, `.reference__body`, `.grid-table__desc`, `.bg-quote__text`, `.memo-q`, `.blk-choice__option`, `.blk-fallback__text` 등)의 `line-height`는 `calc(원래값 * var(--tone-lh-scale, 1))`로 바꿔서, 행간도 톤에 따라 같이 움직이게 함.
- `--ruleH`는 원래부터 톤 클래스에서 재정의돼 있었고(7~8mm), 이번 수정으로 손대지 않음 — 그대로 유지되는지 재확인만 함.
- `--tone-scale`/`--tone-lh-scale` 값은 가이드 1.4표의 본문 크기(15.5/15/14.5px)·행간(1.85/1.8/1.75) 비율을 초5~6(=1) 기준으로 환산해서 넣음(초3~4: 15.5/15=1.03333배, 중등: 14.5/15=0.96667배 — 행간도 같은 방식).
- **elem56 픽셀 동일성 재확인**: elem56은 `--tone-scale:1`/`--tone-lh-scale:1`이라 계산 결과가 원래 고정값과 정확히 같다. 수정 후 `build/index.html`을 elem56 톤으로 다시 렌더링해서(문제 2 지침대로) 확인한 결과, 텍스트 크기·행간·레이아웃에 변화 없음 — 이 문서(신화의숲) 자체의 렌더링은 그대로 유지됨.

**결과**: 세 톤의 `scrollHeight`가 실제로 벌어짐(예: question 500자·excerpt 0자 조합에서 초3~4=386px, 초5~6=376px, 중등=374px). `docs/CAPACITY.md` 3절 "톤 수정 전/후 비교"에 수정 전/후 수치를 나란히 남겨서 효과를 눈으로 확인할 수 있게 해뒀다. `.blk-fallback`은 여전히 같은 변수를 상속하므로 동작에 변화 없음.

### 1.4 분기 테마의 `main-2`/`gold` — 겨울만 값이 있음
- 가이드 1.2표는 `main`/`sub`/`point` 3색만 분기별로 주고, `main-2`(보조 - 안쪽 테두리·괘선용)와 `gold`(표지 강조)는 **겨울 기준 값 하나만** 적혀 있음("보조: main-2 = #31465C(겨울 기준...)").
- 봄·여름·가을 분기의 `main-2`/`gold`는 가이드에 아예 없음. `styles.css`에서는:
  - `main-2`: 각 분기의 `main` 색을 밝게 섞은 계산값(HSL로 밝기만 올림)을 넣어뒀음 — **검증 안 됨**, 실제 봄/여름/가을 학습지 샘플이 나오면 대조 필요.
  - `gold`: 일단 겨울과 같은 값(`#C8A96A`)을 재사용함 — **검증 안 됨**. 가이드 6장 "새 색을 추가하지 않는다"는 지침을 지키려고 새 색을 만들지 않고 기존 겨울 gold를 재사용하는 쪽을 택했는데, 이게 맞는 선택인지는 디자인 확인이 필요함.
- `styles.css`의 `.q-spring`/`.q-summer`/`.q-autumn` 규칙에 이 내용을 주석으로 남겨 둠.

## 2. 발견한 버그와 우회 방법

### 2.1 답란 배경 렌더링 — Chromium PDF 인쇄 경로의 `<div>` + 반복 그라디언트 버그 ⭐가장 중요
- 요청하신 대로 답란을 `<textarea>` → `<div>`로 바꾸고, 원본과 똑같은 `repeating-linear-gradient` 배경(`--ans`)을 그대로 옮겨 붙였더니, **표 셀(`<td>`) 안에 있는 답란 `<div>`에서만** PDF로 내보낼 때 배경이 셀마다 제각각 이상하게 그려지는 문제를 실측으로 확인함(어떤 셀은 안 보이고, 어떤 셀은 선이 엉뚱한 위치에 굵게 그려짐 — 4개 셀이 전부 똑같은 CSS인데도 그랬음, 컴퓨티드 스타일도 전부 동일했음).
- 원인을 좁히려고 다음을 직접 테스트함(`Playwright` + `PyMuPDF`로 PDF를 이미지로 떠서 픽셀 단위로 비교):
  1. `isolation:isolate`/`contain:paint`/`background-attachment:local` 추가 → 효과 없음
  2. 커스텀 프로퍼티(`var(--ans)`) 없이 그라디언트를 직접 하드코딩 → 효과 없음(원인이 CSS 변수는 아님)
  3. **같은 클래스를 `<div>`가 아니라 실제 `<textarea readonly>`로 바꿔서 렌더 → 4개 셀 전부 정상 렌더됨** → `<div>`가 원인이라는 게 확정됨.
- 결론: 이건 **Chromium의 PDF 인쇄 경로가 div 배경의 반복 그라디언트를 표 셀 안에서 잘못 그리는 버그**로 보임(원본이 `<textarea>`를 쓴 이유가 이거였을 수도 있음). 요청서에는 "textarea는 인쇄용으로 부적합하니 div로 바꾸라"고 되어 있어서 **textarea로 되돌리지는 않았고**, 대신 **SVG 타일 이미지 배경**(`background-image: url("data:image/svg+xml,...")` + `background-repeat:repeat` + `background-size: 4px var(--ruleH)`)으로 바꿔서 같은 문제를 피해감. 육안상 원본과 동일하게 보임(아래 3절 검증 참고).
- `styles.css`의 `--ans`/`.answer-lines` 정의에 이 경위를 주석으로 남겨 둠. **템플릿 엔진을 올릴 때도 이 SVG 타일 방식을 그대로 쓰는 걸 권장** — 다시 CSS 그라디언트로 되돌리면 같은 버그가 재발할 수 있음.
- (문제 3 조치) 같은 패턴이 `blk-blanks`/`grid-table` 등 앞으로 추가될 블록에서 재발할 수 있어서, `scripts/check.js`에 **PDF 인쇄 경로 기준**으로 답란 괘선이 실제로 그려지는지 확인하는 항목을 추가함(3.2절 5번 참고) — 화면 렌더 검사로는 이 버그 자체가 재현되지 않아서 의미가 없었기 때문에, 반드시 `page.pdf()`로 뽑은 실제 PDF를 PyMuPDF로 래스터화해서 픽셀을 확인하도록 만듦. `background-image: none`으로 일부러 깨뜨려서 21개 답란 전부가 즉시 잡히는 것도 확인함(오탐/불탐 둘 다 검증).

### 2.2 페이지 박스는 요청서 그대로 구현
- `doc-page.js` 주석에 "직접 @page 규칙을 쓰지 말라"는 경고가 있지만, 요청서에서 "그 컴포넌트를 쓸 때의 제약이니 무시하라"고 명시하셔서 그대로 순정 CSS로 바꿈:
  ```css
  @page { size: A4; margin: 0; }
  .page { width:210mm; height:297mm; overflow:hidden; break-after:page; }
  .page:last-child { break-after:auto; }
  ```
- 화면(스크롤)에서만 그림자·페이지 간 여백을 주고(`@media screen`), 인쇄에는 안 나오게 처리함.

## 3. 검증 결과

### 3.1 포팅 전/후 PDF 픽셀 비교
`Playwright`로 원본 파일과 `build/index.html`을 각각 PDF로 뽑고(`preferCSSPageSize`), `PyMuPDF`로 페이지별 PNG로 변환한 뒤 픽셀 차이를 비교함.

- **페이지 수**: 11 vs 11, 일치.
- **의도한 차이**(요청하신 변경 그 자체):
  - `<textarea>` → `<div>` 답란: 커서 없음, 리사이즈 손잡이(모서리 삼각형) 없음 — 원본은 이 손잡이가 인쇄에도 살짝 보임(브라우저 기본 UI 요소), 포팅본은 없음. **의도된 개선**(요청서 사유: "인쇄용으로 부적합").
- **의도치 않았다가 검수 중 발견해서 고친 차이**(전부 수정 완료):
  - 큰따옴표/작은따옴표가 직선 따옴표(`"`/`'`)로 평탄화됐던 것 → 원본과 동일한 곡선 따옴표(`"…"`/`'…'`, 총 11곳)로 복원함.
  - 답란 배경 괘선이 표 셀 안에서 안 보이거나 위치가 틀어졌던 것 → 2.1절 방법으로 해결.
- **남아있는 미세한 차이**(육안상 구분 안 됨, 계측상으로만 존재):
  - 페이지당 평균 픽셀 차이(RGB 채널 평균) 약 6~14/255(2~5%) 정도가 답란이 있는 모든 페이지에 남아 있음. 원인은 (a) 로컬 폰트 파일이 CDN이 서빙하던 것과 같은 폰트라도 서브셋 방식이 달라 힌팅이 미세하게 다를 수 있음 (b) SVG 타일 기반 답란 괘선이 원본의 CSS 그라디언트 괘선과 픽셀 단위로 완전히 같은 위치/두께는 아님(둘 다 육안으로는 거의 같은 두께의 옅은 선으로 보임). 실제 화면/인쇄물을 나란히 보면 구분이 안 되는 수준이라고 판단함 — `_check_out` 폴더의 스크린샷으로 직접 확인함(스크린샷 파일 자체는 산출물이 아니라서 최종본에는 포함하지 않음).
  - 3단계 페이지의 배경 그림(별자리 사진) 오른쪽에 가느다란 흰 여백이 생기는 현상 — **원본에도 똑같이 있음**(포팅 문제 아님, `object-fit:cover`와 이미지 원본 비율의 조합에서 나오는 원본 디자인의 특성으로 보임).

### 3.2 check.js 결과 (가이드 4.3 체크리스트)
`npm run check`로 11페이지 전체 실행. 결과:
- ✅ 오버플로 없음(11/11)
- ✅ 한 면에 point 색 4곳 이하(11/11)
- ✅ 답란 최소 높이 15mm 이상(11/11)
- ❌ **그림 확대**: 6개 이미지(`cover-sinhwa.jpg`, `fig1~3`, `fig5`, `fig4-constellation.png`)가 가이드 4.4의 "인쇄 150dpi 기준 = mm × 5.9px" 기준보다 원본 해상도가 낮음.

## 4. 인라인 스타일 → 클래스 전환 메모

- 원본 360개 인라인 `style="..."` 전부 제거하고 `styles.css`로 옮김. 남은 예외는 없음(전수 확인 - `grep style=` 결과 0건).
- 반복되는 미세 여백 차이(예: 8-2 문항만 `margin-bottom:1.5mm`, 9번 문항 참고자료 박스 앞은 `2mm`)는 **원본 값 그대로 보존**하되, 새 인라인 스타일 대신 `.q--tight`/`.q--tight2`/`.excerpt--tight`/`.half--gap-sm` 같은 한정적 모디파이어 클래스로 옮김 — 나중에 "왜 이 문항만 여백이 다르지?"를 코드에서 바로 알 수 있게.
- `.half + .half { margin-top:6mm }` 같은 인접 형제 선택자 대신, 간격이 필요한 half에 `.half--gap`/`.half--gap-sm`을 직접 붙이는 방식을 택함 — 템플릿 엔진이 문항 개수에 따라 half를 넣었다 뺐다 할 걸 감안하면, 인접 형제 관계에 암묵적으로 기대는 것보다 명시적인 게 안전함.

## 5. 폰트 로컬화 방법 (문제 1 조치로 전면 재작업)

처음 포팅 때는 `build/index.html` + `blocks-demo.html` + `measure.html`에서 실제 렌더링되는 텍스트만 Playwright로 훑어 554자 서브셋을 만들었었다. 이후 사용자가 지적한 대로, 이 렌더러는 신화의숲 1건이 아니라 **220종의 서로 다른 도서**를 조판하게 되므로 그 554자 밖 글자는 전부 대체 폰트로 조용히 떨어지는 결함이 있었다 — 상세 조치 내역과 검증 결과는 **`docs/FONT_COVERAGE.md`**로 옮겼다. 요지만 남긴다:

- 서브셋 방식을 버리고 Google Fonts CSS2 API의 **기본(무제한) 패밀리 요청**으로 바꿔서, 한글 완성형 11,172자 전체·한글 자모·기본 라틴/문장부호·Noto 기본 상용 한자 세트를 통째로 받음(패밀리+웨이트당 유니코드 레인지 파일 수십~백여 개, 총 934개 + 기호 보충 6개 = 940개, 약 21MB).
- `momo_book_db/momo_book.db`의 실제 문항 텍스트(질문/발췌문/어휘 정의/배경 설명) 전수 스캔으로 이 커버리지를 검증함 — 한글 100%, 한자 181자 중 177자 커버, 나머지 4자는 손상 문서 1건에서만 나온 깨진 데이터라 제외. 인라인 타이포그래피 기호(낫표·가운뎃점·원문자 등) 10종은 기본 요청 밖이라 `text=` 파라미터로 보충 서브셋을 별도로 받아 추가함.
- 검증은 `scripts/check-font-coverage.py`가 매번 DB를 다시 스캔해서 자동으로 재확인함(하드코딩된 글자 목록이 아니라 실행 시점 DB 상태 기준).
- **주의사항(웨이트 개별 요청)은 여전히 유효**: `family=Noto+Sans+KR:wght@400;500;700`처럼 한 요청에 여러 웨이트를 같이 묶어서 요청하면 Google이 웨이트별로 다른 파일이 아니라 같은 파일을 내려주는 경우가 있었음(체크섬으로 확인). 웨이트마다 따로따로 요청해야 함 — 이번 재작업에서도 이 방식을 유지함.
- 다운로드한 웨이트는 가이드 1.3 그대로: Gowun Batang 400/700, Noto Serif KR 400/600/700, Noto Sans KR 400/500/700.
- 폰트 전수 재작업 도중 DB 텍스트에서 폰트 문제와 무관한 **새로운 추출 품질 손상 문서 여러 건**을 추가로 발견함(단일 글자 치환, 비문자 삽입 등) — `docs/FONT_COVERAGE.md` 6절에 목록 정리. 이번 작업 범위 밖(DB 스키마/데이터 변경 금지)이라 고치지 않고 사실만 보고함.

## 6. 디자인 관련 제안 (고치지 않고 제안만 남김)
