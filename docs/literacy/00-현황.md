# aprolabs 프로젝트 구조 현황 (문해력 DB 프로젝트 착수 전 조사)

- 조사 범위: FastAPI 라우터 등록 방식 / SQLite 연결·세션 관리 방식 / `/review`·`/warnings` 화면의 템플릿 패턴 / `verify_agent.py`·`auto_review.py`·`auto_qa_agent.py`의 구조
- 이 문서는 조사만 수행한 결과이며, 조사 과정에서 코드나 DB를 수정하지 않았습니다.
- 새 프로젝트("문해력 향상 DB")를 이 위에 얹을 때 그대로 따를 만한 관례와, 주의해야 할 기존 코드의 특이점(비일관성)을 구분해서 적었습니다.

## 1. FastAPI 라우터 등록 방식

엔트리포인트는 `app/main.py`. 각 도메인이 `app/routers/*.py`에 `APIRouter` 하나씩으로 나뉘어 있고, `main.py`는 이걸 **import + `include_router()` 나열**만 한다 — 라우터 자체의 URL prefix·인증 조건은 각 라우터 파일이 스스로 정의한다.

```python
# app/main.py
from app.routers import questions, upload, suneung, dashboard, answer_keys, crawl, \
    reading_essay, momo_bookshelf, momo_book_review, journal, zoom_summaries
from app.routers import auth as auth_router

app = FastAPI(title="Aprolabs")

app.mount("/static", StaticFiles(directory="app/static"), name="static")
app.mount("/uploads", StaticFiles(directory="uploads"), name="uploads")
app.mount("/momo-images", StaticFiles(directory="momo_book_db/extracted_images"), name="momo_images")

app.include_router(auth_router.router)      # 로그인/로그아웃 — 인증 예외
app.include_router(questions.router)
app.include_router(upload.router)
app.include_router(suneung.router)
...
app.include_router(zoom_summaries.router)   # 가장 최근에 추가된 사례
```

각 라우터 파일 쪽 관례(`app/routers/zoom_summaries.py`, `app/routers/journal.py` 등에서 공통):

```python
router = APIRouter(prefix="/zoom-summaries")
templates = Jinja2Templates(directory="app/templates")

@router.get("", response_class=HTMLResponse)
def index(request: Request, ...): ...
```

**인증**은 라우터 단위가 아니라 `main.py`의 전역 미들웨어 하나로 처리한다 — 화이트리스트(`/login`, `/logout`, `/static/*`, `/uploads/*`)를 제외한 **모든 경로**가 기본으로 보호된다. 새 라우터를 추가해도 별도로 `Depends(require_login)`을 걸 필요 없이 자동으로 보호됨(반대로, 의도적으로 공개해야 하는 경로가 있다면 이 화이트리스트에 추가해야 함):

```python
@app.middleware("http")
async def auth_middleware(request: Request, call_next):
    public_paths = {"/login", "/logout"}
    if request.url.path in public_paths or request.url.path.startswith("/static") \
            or request.url.path.startswith("/uploads"):
        return await call_next(request)
    user_id = get_current_user_id(request)
    if not user_id:
        return RedirectResponse(f"/login?next={request.url.path}", status_code=302)
    return await call_next(request)
```

`@app.on_event("startup")`에서 `init_db()`(SQLAlchemy `Base.metadata.create_all` + 컬럼 마이그레이션)와 최초 admin 계정 생성(`admin@aprolabs.co.kr`)을 수행한다. 새 모델을 추가하면 이 startup 블록의 `from app.models import ...` 목록에 넣어야 `create_all`이 그 테이블을 인식한다(현재 `zoom_summaries`는 SQLAlchemy 모델이 아니라 zoom_reports 쪽 raw sqlite3 DB를 그대로 읽으므로 이 목록에 없음 — 2절 참고).

## 2. SQLite 연결·세션 관리 방식

한 SQLite 파일(`aprolabs.db`)에 대해 **세 가지 다른 접근 방식**이 공존한다. 새 프로젝트를 만들 때 어느 쪽을 따를지 먼저 정해야 한다.

### 2-1. 웹앱 본체 — SQLAlchemy ORM (`app/database.py`)

```python
DATABASE_URL = "sqlite:///./aprolabs.db"
engine = create_engine(DATABASE_URL, connect_args={"check_same_thread": False})
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)

class Base(DeclarativeBase):
    pass

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

def init_db():
    from app.models import question, reading_essay, isbn_cache, reading_list, \
        momo_bookshelf, journal  # noqa
    Base.metadata.create_all(bind=engine)
    _safe_add_columns()  # SQLite는 ALTER TABLE ADD COLUMN IF NOT EXISTS를 지원 안 해서 수동으로 처리
```

라우터 함수는 `db: Session = Depends(get_db)`로 요청 스코프 세션을 받는다. 기존 테이블에 컬럼을 추가할 때는 모델 정의만 바꾸는 게 아니라 `_safe_add_columns()`의 `(table, column, type)` 목록에도 추가해야 실제 컬럼이 생긴다(마이그레이션 도구 없음 — try/except로 이미 있으면 무시).

### 2-2. 백그라운드 태스크 — `SessionLocal()` 직접 생성

`BackgroundTasks.add_task(...)`로 실행되는 함수는 요청이 끝난 뒤 돌기 때문에 `Depends(get_db)`를 쓸 수 없다. `app/routers/suneung.py`의 `run_pipeline()`이 그 예:

```python
def run_pipeline(job_id: str, pdf_path: str):
    from app.database import SessionLocal
    db = SessionLocal()
    try:
        job = db.get(PipelineJob, job_id)
        job.status = "analyzing"; db.commit()
        ...
    finally:
        db.close()
```

### 2-3. 독립 배치/에이전트 스크립트 — raw `sqlite3`, ORM 안 씀

`auto_review.py`, `auto_qa_agent.py`는 FastAPI 앱 프로세스 밖에서 CLI로 직접 실행되는 별도 스크립트다. SQLAlchemy를 전혀 쓰지 않고 같은 `aprolabs.db` 파일을 **raw `sqlite3.connect()`로 직접** 열어서 SQL을 그대로 실행한다:

```python
# auto_review.py
DB_PATH = os.path.join(os.path.dirname(__file__), "aprolabs.db")
conn = sqlite3.connect(DB_PATH)
cur = conn.cursor()
cur.execute("SELECT id, filename, raw_result, segments FROM pipeline_jobs WHERE raw_result IS NOT NULL")
```

`pipeline_jobs.raw_result`는 JSON 텍스트 컬럼이라 `json.loads()`/`json.dumps()`로 직접 읽고 다시 써넣는다(ORM의 JSON 컬럼 타입을 안 씀 — SQLAlchemy 쪽 `PipelineJob` 모델과는 별개 경로로 같은 데이터를 만짐). **이 패턴은 이 프로젝트 전반에 걸친 관례**로, `zoom_reports/`의 `generate_reports.py`/`correct_reports.py`/`collector.py` 등도 동일하게 "웹앱은 ORM, 배치 스크립트는 raw sqlite3"로 나뉜다.

**주의(비일관성, 새 프로젝트에서 피할 것)**: `auto_qa_agent.py`는 `DB_PATH`/`BASE_DIR`이 **서버 절대경로로 하드코딩**돼 있다(`/home/chsh82/aprolabs/aprolabs.db`, `sys.path.insert(0, '/home/chsh82/aprolabs')`). 로컬(Windows)에서는 이 경로가 존재하지 않아 실행이 안 된다 — 서버에만 배포해서 쓰는 스크립트로 보인다. `auto_review.py`는 반대로 `os.path.dirname(__file__)` 기준 상대경로라 로컬/서버 어디서나 돌아간다. **새 스크립트는 `auto_review.py` 쪽 방식(포터블)을 따르는 게 안전.**

### 2-4. 참고: `zoom_reports/`의 완전히 다른 패턴

`zoom_reports/`는 아예 별개 DB(`momo_zoom.db`)를 쓰고, 조회용과 쓰기용 커넥션을 명시적으로 분리한다(`app/routers/zoom_summaries.py`):

```python
def get_zoom_db():      # 조회 - SQLite URI mode=ro로 열어 쓰기 자체를 DB 레벨에서 차단
    uri = f"file:{db_path.as_posix()}?mode=ro"
    return sqlite3.connect(uri, uri=True)

def get_zoom_db_rw():   # 쓰기 - save/approve 라우트에서만 사용
    return sqlite3.connect(str(db_path))
```

문해력 DB가 여러 프로세스(웹 UI + 배치 스크립트)에서 같은 DB를 만지게 된다면, 이 mode=ro 분리 패턴이 "배치가 실수로 화면 쪼가리 코드에서 쓰기를 하는" 사고를 막는 데 참고할 만하다.

## 3. `/review`, `/warnings` 화면의 템플릿 패턴 (`app/routers/suneung.py` + `app/templates/suneung/`)

### 3-1. 공통 골격 — `base.html`

모든 페이지는 `{% extends "base.html" %}`. `base.html`은 상단 헤더 + 좌측 사이드바(정적 링크 목록, `{% if request.url.path.startswith('/xxx') %}`로 active 표시) + 메인 영역으로 구성. 메인 영역은 두 가지 블록 중 하나를 오버라이드해서 쓴다:

- `{% block content %}` — 기본. `max-w-4xl mx-auto` 중앙 정렬 래퍼 안에 렌더링(목록/폼 페이지 대부분).
- `{% block content_wrapper %}` — 전체를 오버라이드. `review.html`처럼 뷰포트 전체를 3분할 패널로 써야 하는 페이지가 이걸 씀(`display:flex;height:100%;overflow:hidden` 등 자체 레이아웃).

CSS는 Tailwind CDN 스크립트 한 줄(`<script src="https://cdn.tailwindcss.com?plugins=typography">`)로 로드 — 별도 빌드 과정 없음. 다만 실제 스타일은 **Tailwind 유틸리티 클래스와 raw `style="..."` 인라인이 같은 파일 안에서 혼용**되어 있다(`warnings.html`의 카드형 요약 UI는 인라인 style, 상단 헤더는 Tailwind 클래스). 일관된 컨벤션이 아니라 페이지마다 다르므로, 새 화면을 만들 때 어느 쪽으로 통일할지는 자유롭게 정하면 됨.

라우터 쪽에는 사이드바에 필요한 공통 데이터(카테고리별 문항 수 등)를 매번 만들지 않도록 헬퍼를 둔다:

```python
def _base_ctx(db: Session, **kwargs):
    counts = {cat: db.query(Question).filter(Question.category == cat).count() for cat in CATEGORIES}
    return {"categories": CATEGORIES, "category_counts": counts, **kwargs}
```

### 3-2. 프론트엔드 — 프레임워크 없음, 서버 렌더 + fetch()

React/Vue 등 프레임워크는 전혀 없음. 페이지 하단 `<script>` 블록에 vanilla JS를 직접 쓰고, `fetch()`로 **같은 라우터 파일의 POST 엔드포인트**를 호출해 JSON을 받은 뒤 DOM을 직접 조작한다:

```js
// review.html
await fetch('/suneung/review/{{ job.id }}/save', {method:'POST', body: ...});
const res = await fetch('/suneung/review/{{ job.id }}/rerun-agent', {method:'POST'});
const r = await fetch('/suneung/review/{{ job.id }}/warning-judgment', {method:'POST', body: JSON.stringify({key, judgment})});
```

`job.id` 등 서버 값은 Jinja 템플릿 변수로 JS 문자열에 직접 박아넣는 방식(`{{ job.id }}`) — 별도 data attribute나 JSON 스크립트 태그를 안 씀.

**상태 폴링**은 웹소켓/SSE 없이 `setInterval` + `fetch` + `location.reload()`로 처리:

```js
setInterval(async () => {
  const d = await (await fetch('/suneung/jobs/status/{{ job.id }}')).json();
  document.getElementById('status-txt').textContent = d.status;
  if (['reviewing', 'done'].includes(d.status)) location.reload();
}, 3000);
```

### 3-3. `/warnings` — `warnings_list()` → `suneung/warnings.html` (295줄)

`PipelineJob.raw_result`(JSON 컬럼)에 들어있는 `verify_corrections`(경고 원본), `warning_reviews`(사람 판정), `ai_reviews`(auto_review.py가 채워넣는 AI 판정)를 라우터에서 Python으로 categorize·group·집계한 뒤 템플릿에 dict로 넘긴다. 화면은:
- 카테고리별(`텍스트불일치`/`bracket텍스트불일치`/`지문못찾음`/`문항못찾음`/`밑줄못찾음`/`기타`) 그룹 테이블
- 사람 판정 vs AI 판정 요약 카드(오탐/실제오류/보류/미판정 건수), 둘이 다르면 `disagree` 플래그
- 판정 버튼 클릭 → `fetch(.../warning-judgment)` POST → `raw_result.warning_reviews`에 저장

### 3-4. `/review/{job_id}` — `review()` → `suneung/review.html` (2574줄, 이 프로젝트에서 가장 큰 템플릿)

단일 `PipelineJob`을 불러와 통째로 넘기고(`_base_ctx(db, request=request, job=job)`), 화면 안에서 모든 편집이 일어난다:
- 왼쪽 PDF 패널: pdf.js 등 클라이언트 렌더러가 아니라, **업로드 시점에 미리 PNG로 렌더링해둔 페이지 이미지**를 `/suneung/review/{job_id}/pages`로 목록만 받아 `<img>`로 순회 표시(`get_page_images()` — `uploads/{job_id}/pages/` 또는 `images/` 디렉토리 탐색)
- 문항/지문 편집 폼 + 이미지 crop + 경고별 판정 + "AI 재실행"(`rerun-agent` → verify_agent를 그 자리에서 다시 호출) + "승인"(`approve`) 등 다수의 POST 액션이 각각 별도 엔드포인트로 쪼개져 있고, 프론트는 그 각각을 fetch로 호출

## 4. `verify_agent.py` / `auto_review.py` / `auto_qa_agent.py` 구조 비교

세 스크립트는 역할이 뚜렷이 다르고, 앱과의 결합 방식도 다르다.

| | `verify_agent.py` | `auto_review.py` | `auto_qa_agent.py` |
|---|---|---|---|
| 모델 | Gemini (`gemini-2.0-flash`) | Claude Haiku (`claude-haiku-4-5-20251001`) | Claude Sonnet (`claude-sonnet-4-6`) |
| 앱과의 관계 | **인라인 라이브러리** — `suneung.py`가 `from verify_agent import run`으로 직접 import해 파이프라인 안에서 호출 | **독립 CLI** — 앱이 import하지 않음, 사람이 터미널에서 실행 | **독립 CLI** — 앱이 import하지 않음 |
| 실행 시점 | 업로드 파이프라인의 "Phase 3.5"(자동) + `/review/{id}/rerun-agent`(수동 재실행) | 사람이 필요할 때 수동 실행 | 사람이 필요할 때 수동 실행 |
| 입력 | PDF 페이지 이미지(PyMuPDF로 렌더링) + segments JSON | DB의 `pipeline_jobs.raw_result`(이미 verify_agent가 만든 경고 목록) | PDF 페이지 이미지 + DB의 문항 데이터 |
| 출력 | Pydantic `CorrectionResult`(교정된 segments + fixed/warning 목록) — 호출부가 DB에 반영 | DB에 직접 write-back (`raw_result["ai_reviews"][key] = {...}`) | DB에는 안 씀 — `golden_tests/qa_report_*.json` 리포트 파일 생성 |
| 경로 방식 | 상대경로(포터블) | 상대경로(포터블, `os.path.dirname(__file__)`) | **절대경로 하드코딩**(서버 전용, `/home/chsh82/aprolabs/...`) |
| 핵심 구조 | Pydantic 모델 다수(`Correction`/`Passage`/`Question`/`Segments`/`CorrectionResult`) + `VerifyAgent` 클래스(메서드별로 페이지 추출→지문/문항 대조→텍스트/괄호/밑줄/보기/이미지/선택지 교정 단계 분리) + 모듈 함수 `run()`이 공개 진입점 | 함수형: `categorize()`(경고 메시지 → 카테고리) → `build_context()`/`build_prompt()`(DB 데이터로 프롬프트 구성) → `parse_response()` → `main()`이 sqlite3로 직접 순회 | 함수형: `get_jobs()`(대상 조회) → `analyze_page()`(Vision 호출) → `compare()`(Vision 결과 vs DB 대조, `difflib` 유사도) → `run_job()` → `main()`(파일별 리포트 저장) |
| CLI 옵션 | `python verify_agent.py <pdf> <segments.json> [출력.json]` | `--dry-run --force --cat CAT --limit N` | `--file --pages --all --dry-run` |

**verify_agent.py**는 이 셋 중 유일하게 "실시간 파이프라인의 일부"다. 업로드 → 텍스트 추출 → (Anthropic 태깅) → **verify_agent(Gemini)로 PDF 대조·교정** → 정답 파싱 순서로, `run_pipeline()`(백그라운드 태스크) 안에서 동기 함수 호출로 이어진다. `ENABLE_ANTHROPIC`/`USE_ANTHROPIC` 플래그로 이 유료 API 단계 전체를 켜고 끌 수 있게 되어 있다(비용 제어 관례).

**auto_review.py**/**auto_qa_agent.py**는 파이프라인이 끝난 뒤 사람이 필요할 때 따로 돌리는 "2차 검증" 배치다 — DB를 직접 열어 읽고(필요하면 쓰고) 끝난다. `zoom_reports/generate_reports.py`·`correct_reports.py`와 같은 성격("생성 파이프라인과는 별도 프로세스로, 같은 DB를 raw sqlite3로 직접 다루는 배치 스크립트")이라, 문해력 DB 쪽에서 유사한 2차 검증/보정 단계가 필요하다면 이 셋 중 하나의 구조를 그대로 본뜨면 될 것으로 보인다.

## 5. 문해력 DB 프로젝트에 적용할 때 참고할 점 (요약)

- **라우터**: `app/routers/새이름.py`에 `APIRouter(prefix="/...")` 만들고 `main.py`에 import + `include_router()` 한 줄 추가하면 끝. 인증은 자동으로 걸림(화이트리스트에 없으면).
- **DB**: 웹 화면에서 SQLAlchemy로 다룰 데이터라면 `app/models/`에 모델 추가 + `main.py` startup의 import 목록 + `init_db()`의 `_safe_add_columns()`에 새 컬럼 등록. 별도 배치 스크립트가 필요하면 `auto_review.py`처럼 상대경로 기반 raw `sqlite3.connect()`로 — `auto_qa_agent.py`의 하드코딩된 절대경로는 따라가지 말 것.
- **화면**: `base.html` 상속 + `content` 블록(목록/폼) 또는 `content_wrapper`(전체 화면 커스텀 레이아웃)만 골라서 쓰면 사이드바·인증·Tailwind는 공짜로 따라옴. 인터랙션은 프레임워크 없이 vanilla JS `fetch()` + 같은 라우터의 POST 엔드포인트로 충분히 구현 가능(이 프로젝트의 확립된 관례).
- **AI 검증/보정 단계가 필요하면**: 파이프라인 실시간 일부로 넣을지(verify_agent 방식, in-process import) 아니면 사후 배치로 뺄지(auto_review/auto_qa_agent 방식, 독립 CLI) 먼저 정할 것 — 비용·응답속도 트레이드오프가 다르다.

## 6. krdict 자료원 메모

Phase 2(속담·관용구 수집, `docs/literacy/02-속담수집.md`) 진행 중 확인한 krdict(한국어기초사전) 자체에 대한 사실. 이후 Phase 3(어휘 수집)에서 그대로 참고할 것.

- **통계 페이지**: https://krdict.korean.go.kr/statistic/dicStat
- **표제어 규모**: 53,671건(단어 51,555 + 구 1,120 + 문법·표현 996). 부표제어(속담·관용구)는 별도로 2,884건(속담 657 + 관용구 2,227) — "표제어"와 "부표제어"는 통계 페이지에서부터 이미 분리된 카테고리다.
- **등급별 분포**(표제어 53,671건 기준, 실제 덤프에서 `vocabularyLevel` 필드를 직접 집계해 대조 확인함):

  | 등급 | 건수 |
  |---|---|
  | 초급 | 2,545 |
  | 중급 | 9,068 |
  | 고급 | 37,024 |
  | 없음(등급 미부여) | 5,034 |

- **⚠️ Phase 3 경고 - krdict 등급은 한국 학생 학년과 다른 기준이다.** krdict는 "한국어를 배우는 외국인 학습자"를 대상으로 하는 학습자 사전이라, `vocabularyLevel`(초급/중급/고급)은 **외국어로서의 한국어 숙달도** 기준이지 한국 초중고 학년별 국어 교육과정과 매핑되지 않는다. 예를 들어 한국 초등학생이 당연히 아는 단어가 "고급"으로 분류돼 있을 수 있다. Phase 3에서 `terms.grade_level`(1~12, 초1~고3)을 자동 산정할 때 이 3단계 등급을 그대로 치환하면 안 되고, 별도의 매핑 기준이나 보정이 필요하다 — 지금 스키마 변경은 안 하고 기록만 남긴다.
- **표준국어대사전(stdict)과의 규모 비교**: 속담 7,436 / 관용구 3,886 (krdict의 약 11배 / 1.7배). krdict은 학습자 사전이라 속담·관용구가 상대적으로 적다는 게 실측으로 확인됨.
  - krdict은 로그인 없이 즉시 "전체 내려받기"가 가능했던 반면, stdict은 검색 결과상 회원가입 후 로그인 → "내 정보 관리" → "사전 내려받기" 경로가 필요해 보임(직접 시도는 안 해봄 - 계정이 없어 확인 못 함). stdict을 자료원으로 쓸 계획이면 계정 발급이 먼저 필요하다.

**Phase 3-2 갱신**: `grade_level`(1~12, 학년 단위) 대신 `level`(0~6, 2개 학년 묶음 단위)을 실제 운용 등급 기준으로 도입했다 — 이후 모든 작업은 `level` 기준으로 돌아간다. 자세한 내용은 `docs/literacy/04-스키마리딩어휘.md` 참고.

**⚠️ Phase 5 정의 명확화 — `level`의 의미.** `level`은 **"이 단어를 배우는 학년 단계"**이지 **"이 단어의 난이도"**가 아니다. 교재 어휘(`source='momo-textbook'`)는 그 학년 교재 지문에서 학생이 아직 모르는 새 단어를 가르치려고 추출된 것이라, 해당 학년 학생이 이미 알고 있는 단어가 아니다. 예를 들어 `level=0`(초1~2)에 "고약하다", "케케묵다", "고즈넉하다" 같은 정서·상태 어휘가 있는 건 레벨 산정 오류가 아니라 - 스토리텔링 지문(전래동화·인문예술 단원)에서 그 학년 학생에게 처음 가르치는 어휘이기 때문이다(2026-09-01 검수 대화에서 확인, 교재 원본 level·quarter·week 대조로 매핑 자체는 정상임을 확인함). **따라서 `level`만으로 문항 난이도를 판단하면 안 된다.** 퀴즈 생성/검수 단계에서 이 둘을 혼동하지 않도록 주의가 필요하다 - 자세한 사례는 `docs/literacy/05-퀴즈생성-결과.md`의 검수 결과 참고.
