## 1. 요약

기존 7,087건(terms) 중 262건을 목표로 어휘 210 + 속담 50 문항을 생성했다. 실제로는

## 2. 사용한 모델과 파라미터

- 모델: `claude-sonnet-4-6` (`.env`의 `LITERACY_QUIZ_MODEL`에서 읽음 — 코드에 하드코딩하지 않음)
- `max_tokens`: 4000 (배치당)
- 배치 크기: 최대 10개(같은 `sense_category` 안에서 묶고, 없으면 레벨로 묶음)
- 재시도: 배치 단위 최대 3회, 실패 시 해당 배치만 건너뛰고 계속 진행
- 호출 사이 딜레이: 1초
- 대상 추출 시드: `20260831`(레벨/속담 풀에서 `random.Random(seed + level)`로 셔플 후 상위 N개 선택 — 재현 가능)
- **정답 위치 셔플은 추출 시드와 분리된, 시드 없는(OS 엔트로피) 별도 `random.Random()`을 쓴다.** 처음엔 `random.Random(SEED + term_id)`로 만들어서 추출 시드와 얽혀 있었는데, 사용자가 "셔플에는 시드를 고정하면 안 된다"고 지적해 분리했다. 5,000개로 편향 여부를 직접 검증한 결과 원래 방식도 통계적으로 치우치진 않았지만(1~4번 각각 24~26%), 추출과 셔플이 같은 시드 계열을 공유할 이유가 없다는 지적은 타당했다.

## 3. 사용한 프롬프트 전문

`scripts/literacy/quiz_prompt.py`의 `build_batch_prompt()`가 매 배치마다 아래 틀을 채워서 만든다. 대상 목록과 `context_label`(배치의 공통 sense_category/레벨)만 배치마다 바뀐다.

```
너는 초중고 학생용 국어 {낱말|속담} 4지선다 문항의 오답을 만드는 역할이다.
아래 {N}개 {낱말|속담}마다 정답 뜻풀이가 주어진다. 각각에 대해 오답 3개씩 만들어라.
이번 배치의 공통 주제/레벨: {context_label}

오답 3개를 만들 때 반드시 지킬 것:

1. 방향을 섞어라 - 반대(정답과 반대되는 뜻), 인접(비슷하지만 다른 뜻),
   부분오류(일부만 맞고 핵심이 틀림) 세 방향을 섞어서 만든다.

2. 오답이 정답 쪽으로 수렴하면 안 된다. "정도만 다른" 오답(예: 정답이
   "다르다"인데 오답이 "조금 비슷하다")은 정답과 양립 가능해서 정답이
   두 개가 되는 결과를 낳는다. 오답은 정답과 명백히 다른 사실을 말해야
   한다.

3. 종결 형태를 정답과 일치시켜라. 정답이 "~하다."로 끝나면 오답도 전부
   "~하다."로 끝난다. 마침표 유무까지 맞춘다.

4. 길이를 정답의 ±50% 이내로 맞춰라. 정답이 20자면 오답은 10~30자.

5. 도입구(문장 서두)를 정답과 통일하는 건 정답의 문장 구조가 그것을
   자연스럽게 허용할 때만 한다. 억지로 맞춰서 문장이 어색해지면 하지
   않는다 - 맞춰야 하는 건 종결형·길이·마침표이고, 문장 구조는 자연스러움이
   우선이다.

6. 오답에 "아니다", "않다", "못하다" 같은 단순 부정어로만 만들지 않는다.

7. 정답 문장은 절대 다시 쓰지 마라. 그대로 사용한다.

아래는 형식을 지킨 예시다(방향을 참고하고, 그대로 베끼지는 마라):

- 단어: 가르다
  정답: 쪼개거나 나누어 따로따로 되게 하다.
  오답: 덮거나 가려서 보이지 않게 하다.
  오답: 묶거나 연결하여 붙이다.
  오답: 합치거나 모아서 하나로 만들다.

- 단어: 구분
  정답: 일정한 기준에 따라 전체를 몇 개로 갈라 나눔.
  오답: 비슷한 것들을 같은 종류끼리 모아 둠.
  오답: 여러 개로 나뉜 것을 하나로 합쳐 놓음.
  오답: 일정한 기준에 따라 크기 순서로 늘어놓음.

- 단어: 다르다
  정답: 비교가 되는 두 대상이 서로 같지 아니하다.
  오답: 비교가 되는 두 대상이 서로 완전히 같다.
  오답: 비교가 되는 두 대상이 서로 짝을 이루고 있다.
  오답: 비교가 되는 두 대상이 서로 관련이 없다.

- 단어: 감상
  정답: 주로 예술 작품을 이해하여 즐기고 평가함.
  오답: 주로 예술 작품을 훼손하거나 망가뜨림.
  오답: 주로 예술 작품을 새로 만들어 냄.
  오답: 주로 예술 작품을 팔거나 사서 거래함.

- 단어: 규칙
  정답: 여러 사람이 다 같이 지키기로 작정한 법칙. 또는 제정된 질서.
  오답: 개인이 혼자 정한 취향이나 선호.
  오답: 그때그때 형편에 따라 임시로 정해 둔 약속.
  오답: 지키지 않아도 되는 특별한 예외 사항.

이제 아래 대상에 대해 오답을 만들어라:

- term_id: {id}
  {낱말|속담}: {headword}
  정답: {definition}
  (배치 내 대상 수만큼 반복)

출력은 다른 설명 없이 아래 JSON 형식만 출력하라(코드블록 없이, 순수 JSON 텍스트만):
{"items": [{"term_id": 123, "distractors": ["오답1", "오답2", "오답3"]}, ...]}
배열에는 위 {N}개 term_id가 전부, 그리고 그것만 있어야 한다.
```

### few-shot 5개를 만든 방법

원본 `raw/schema-reading/`의 어휘퀴즈DB.xlsx(선생님이 직접 만들어 쓰던 검증된 문항
338개)에서 few-shot을 고르려고 했으나, **엄격한 기준(마침표 일치 + 길이 ±30%)으로는
338건 중 0건이 통과**했다(마침표만 일치하는 건 3건, 길이만 맞는 건 73건, 둘 다
맞는 건 0건). 그래서 오답의 "방향"(반대/인접/부분오류)이 뚜렷한 5개를 먼저 고르고,
방향은 그대로 유지한 채 종결형·마침표·길이만 교정하는 방식으로 만들었다 — 새로
창작하지 않았다. "가르다"는 지시서 5-3절이 직접 예로 든 결함 문항을 그대로 교정한
것이다.

교정 과정에서 "다르다"의 오답 2개("거의 유사하다"/"조금 비슷하다")를 사용자가
재검토를 지시해 폐기했다 - 둘 다 "완전히 같지는 않다"는 의미로 정답과 양립
가능해서 정답이 두 개가 되는 문제가 있었다. 이 교훈이 위 프롬프트 규칙 2번
("수렴 금지")이다. "규칙"의 오답은 처음엔 도입구("여러 사람이")를 억지로
통일해서 문장이 어색해졌는데, 이걸 사용자가 지적해 도입구는 자연스럽게 두고
종결형·길이만 맞추도록 다시 고쳤다 - 이 교훈이 규칙 5번이다.

## 4. 오답 생성 전략과 근거

지시서 5-2절 원칙(같은 `sense_category`+레벨 안에서 뽑거나 참고해 생성)에 따라,
`sense_category`가 있는 항목(schemareading-schema, momo-textbook 일부)은 같은
sense_category로 배치를 묶었다. `sense_category`가 없는 항목(schemareading-tooldict
전체)은 같은 레벨로 묶었다. 배치 안에서 LLM이 도메인 맥락(`context_label`)을 참고해
오답 방향(반대/인접/부분오류)을 정하도록 했고, 다른 항목의 실제 정답 텍스트를
오답 재료로 직접 주입하지는 않았다(다른 표제어의 뜻풀이를 오답에 그대로 베끼는
결과를 피하기 위함).

## 5. 단서 노출 방지 규칙과 기존 338문항에서 발견된 문제

지시서가 예로 든 "가르다"(정답만 마침표로 끝남), "쓰다"(정답이 오답보다 4배 이상
길었음) 외에도, 실제로 전수조사해보니 원본 338문항 자체가 이 결함을 광범위하게
갖고 있었다:

| 검사 | 338건 중 통과 |
|---|---|
| 마침표 유무가 4개 선택지 전부 일치 | 3건(0.9%) |
| 정답 길이가 오답 평균의 ±30% 안 | 73건(21.6%) |
| 둘 다 통과 | **0건** |

즉 원본 문항의 가치는 형식이 아니라 **오답이 어느 방향으로 비트는지**에 있었다.
그래서 few-shot도 "오답 방향은 보존, 형식만 교정"하는 방식으로 만들었다(3절 참고).

## 7. 자동 품질 검사가 잡지 못한 문제

8절 자동 품질 검사(정답 위치 분포/최장 비율/종결형·마침표 일치율/길이 편차/오답
중복)는 **252건 전부 통과**했다(정답 최장 비율 34.9% < 40%, 종결형·마침표 일치율
98.8%, 오답 중복 0건). 하지만 이 지표들은 전부 **형식** 검사다. 검증 순서 5번(레벨
0/3/6에서 무작위 10문항 육안 검토)에서 형식은 멀쩡하지만 **내용이 잘못된 문항**
2종류를 발견했다 - 자동 검사로는 절대 못 잡는 문제다.

### 7-1. 원본 데이터 오류 — "통계"의 정답 자체가 틀림

`momo-textbook`, `external_id=1238`, headword="통계". `terms.definition`이
`"한 번에 몰아서 대충 짐작으로 계산함."`으로 저장돼 있는데, 이건 "통계"의 뜻이
아니라 "어림/짐작"류 다른 단어의 뜻풀이다. 지시서 5-1절 규칙("정답 문장은 절대
다시 쓰지 마라")을 그대로 지켰기 때문에, LLM이 만든 오답 3개는 형식·방향 모두
정상이었지만 정답 자체가 오답이 되는 결과가 나왔다. 주변 행(external_id
1233~1240)은 전부 정상이라 이전에 발견했던 "연속 블록 밀림"과는 다른, **단독
오류**로 보인다. 이번 단계에서 `terms`는 읽기만 하므로 원본을 고치지 않았다.

**처리**: `quiz_items`에서 삭제하지 않고 `review_status='제외'`로 변경했다.
`quiz_items` 테이블에는 `note` 컬럼이 없어서(스키마: id/term_id/quiz_type/question/
correct_answer/distractors/difficulty/generated_by/model/review_status/created_at)
"원본 정답 오류로 제외"라는 문구를 DB에 남기지는 못했고, 이 문서에 기록한다.

**이번 단계 범위가 아니라 수정은 별도 작업으로 미룬다.** 여기 목록만 남긴다.

**처리**: 이번 표본에 걸린 3건(`외04`/`이론01`/`개설02`)은 `quiz_items`에서
`review_status='제외'`로 변경했다. 나머지 25건은 아직 어떤 quiz_items에도 없다.

### 7-3. 다음 대량 생성 때 반드시 할 것

**형식 품질 검사(8절)를 전부 통과해도 내용이 틀릴 수 있다.** 이번엔 육안 표본
10건(3.9%) 검토에서 2종류의 실제 문제(원본 데이터 오류 1건, 파싱 누락 3건)가
나왔다 - 표본 비율로 보면 전체 252건 중 훨씬 더 많은 문제가 숨어 있을 가능성이
있다. 다음에 대량 생성할 때는:

1. **자동 품질 검사와 별도로, 생성이 끝난 뒤 사람이 무작위 표본을 육안으로
   읽어보는 단계를 필수로 넣어라.** 이번 단계에서 배운 가장 큰 교훈이다.
2. tooldict의 숫자 접미사(28건) 같은, 파싱 시점엔 눈에 안 띄지만 생성물에서
   드러나는 원본 데이터 결함이 더 있을 수 있다.
3. `terms.definition`이 실제로 그 헤드워드의 뜻인지 자동으로 검증할 방법은
   없다(이건 애초에 이 파일럿의 목적이기도 하다 - "DB가 쓸 만한지 확인").
   사람 검수가 유일한 안전망이다.
