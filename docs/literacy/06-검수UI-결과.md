## 3. X 판정 사유 코드 목록

지시서 5절이 지정한 6개를 그대로 썼다. `quiz_items.reject_reason`에 코드 그대로 저장한다(자유 메모인 `note`와 분리 - 집계 대상이라 컬럼으로 둠, 3절 참고).

1. 정답이 틀림
2. 오답이 너무 쉬움 (소거법으로 풀림)
3. 오답이 정답에 가까움 (정답이 둘)
4. 표기 문제 (숫자 접미사 등)
5. 레벨 부적절
6. 기타 (메모 필수)

## 4. `review_status` 값의 의미

| 값 | 의미 |
|---|---|
| `검수전` | 아직 아무도 판정하지 않음(기본값) |
| `검수완료` | 문항: O 판정 / 뜻풀이: 작성 완료 / 레벨: 레벨 부여 완료 |
| `보류` | 문항: 판단을 나중으로 미룸(재검수 대상으로 남음) |
| `제외` | 문항: X 판정(오류·부적절) / 레벨: "해당 없음"(교육과정에 낼 만하지 않음) |

`reviewed_at`이 `NULL`인 행은 아직 이 검수 UI를 거치지 않은 행이다(재검수 대상을 고르는 기준으로 쓰인다 - 지시서 3절의 도입 이유 그대로).

## 5. AI 자동 생성을 의도적으로 넣지 않은 이유

뜻풀이 작성 화면(`/literacy/review/definition`)에 AI 자동 생성 버튼을 넣지
않았다. 지시서 6절이 명시한 이유를 그대로 따른다: **화면부터 완성하고, 자동
생성은 별도 단계에서 결정한다.** 지금 넣으면 검수 UI가 완성되기도 전에 724건이
AI 초안으로 먼저 채워져 버려서, "빈 뜻풀이를 사람이 판단해서 채운다"는 화면의
목적 자체가 왜곡된다. 대신 "같은 소분류의 다른 어휘 뜻풀이 3~5개"를 참고 자료로
보여줘서 사람이 직접 쓸 때 문체를 맞추는 데 쓰도록 했다.

## 6. 구현 메모

- **소분류 매칭**: `terms`에는 "소분류" 전용 컬럼이 없고 Phase 3-2에서 `note`에
  `"소분류: ... / 주차: ..."` 텍스트로만 넣었다. 뜻풀이 화면에서 참고 어휘를
  찾을 때 이 텍스트를 정규식(`소분류:\s*([^/]+)`)으로 파싱해서 매칭한다 -
  스키마를 바꾸지 않고 기존 텍스트를 그대로 활용.
- **이전/다음 이동**: 문항·뜻풀이 화면은 `id` 순서로, 레벨 부여 화면은
  지시서 7절이 요구한 "뜻풀이가 짧고 흔한 것부터" 순서(`LENGTH(definition) ASC,
  id ASC`)로 이동한다. "다음"은 아직 검수 안 된 항목을 우선 찾고, "이전"은
  상태와 무관하게 정렬 순서상 바로 앞 항목으로 이동한다 - 이미 판정한 항목도
  되돌아가서 다시 볼 수 있게 하기 위함(지시서 4-3절 "잘못 눌렀을 때 되돌릴 수
  있어야 한다").
- **진행률 계산**: 대상 총량이 검수가 진행될수록 줄어들지 않도록, "총량 = 현재
  남은 것(`검수전`/빈 뜻풀이/`level IS NULL`) + 이미 검수한 것(`reviewed_at IS
  NOT NULL`)"로 고정했다. 예를 들어 문항 화면은 248(현재 검수전) + 0(아직
  `reviewed_at` 없음) = 248로 시작하고, 판정이 쌓여도 총량은 248을 유지한다.
- `base.html`에 사이드바 링크 한 줄(`📘 문해력 DB 검수` → `/literacy/review`)만
  추가했다. 사용자 승인 사항("기존 템플릿 수정 금지"는 기존 화면을 망가뜨리지
  말라는 뜻이지 링크 추가까지 막는 게 아님) - 추가 후 기존 화면 정상 동작을
  실측 확인했다(9절 참고).

## 7. 검증 (지시서 9절 10개 항목)

1. **마이그레이션**: `quiz_items.note`/`reject_reason`/`reviewed_at`, `terms.reviewed_at` 4개 컬럼 추가 확인. 재실행 시 "이미 존재함 - 건너뜀" 출력, 컬럼 중복 추가 없음(재실행 안전).
2. **세 화면 동작 + 대상 건수**: 로그인 후 세 화면 전부 200 OK. 대상 건수 실측 - 문항 248 / 뜻풀이 724 / 레벨 2,884, 지시서 예상치와 정확히 일치(뜻풀이는 "약 697"이 아니라 724가 맞다고 사용자가 이미 확인함).
3. **실제 저장 3건씩**: 세 화면 각각 3건씩 실제로 저장하고 DB 반영을 확인했다(quiz_items 3건: O/X/보류, terms 정의 3건, terms 레벨 3건 - 레벨0/레벨3/"해당없음" 각각). **검증 후 이 9건은 전부 검증 전 상태로 원복했다** - 실제 검수 데이터가 아니라 테스트값("테스트 O" 등)이었기 때문에, 검증이 끝난 뒤 마이그레이션 직전 백업에서 원래 값을 읽어와 되돌렸다(뒤에 다시 카운트 검증 - 248/724/2,884 그대로, `reviewed_at` 남은 것 0건).
4. **`reviewed_at` 기록**: 저장 시점에 정확히 기록됨을 실측 확인(위 3번 검증 중 확인, 이후 원복).
5. **이전 건 돌아가기**: 서버가 계산한 `prev_id`/`next_id`가 요청대로 나오는지 확인(예: id=1 판정 후 next_id=4로 정확히 건너뜀 - 2,3도 검수됨을 인지).
6. **단축키**: 코드 리뷰로 확인(JS 키 리스너 로직 - `1`/`2`/`3`/방향키/`0`~`6`). **실제 브라우저에서 키 입력을 눌러보는 시각적 테스트는 하지 못했다** - 이 환경에 브라우저 자동화 도구가 없어서 HTTP 요청(curl)과 코드 리뷰로만 검증했다. 실제 사용 전에 브라우저에서 한 번 눌러보시는 걸 권장한다.
7. **저장 실패 표시**: `reject_reason` 없이 X 저장 시도 → `{"ok":false,"error":"X 판정은 사유가 필요합니다"}` 정상 반환 및 프론트에서 표시됨. 잘못된 요청(존재하지 않는 id) → 명확한 에러 메시지. 완전히 깨진 요청(비-JSON 바디)은 서버가 500을 반환하지만 프론트의 `try/catch`가 `fetch` 예외를 잡아 화면에 표시하므로 "조용히 실패"하지는 않는다.
8. **기존 기능 무손상**: `/literacy/health`(200), `/suneung/db`(200), `/` (200) 정상. **`/suneung/warnings`와 `/suneung/jobs`가 500 오류를 냈으나, 원인은 이번 작업과 무관하다** - `pipeline_jobs.grade` 컬럼이 로컬 `aprolabs.db`에 없어서 발생하는 기존 스키마 드리프트다(코드에서 `PipelineJob` 모델은 이 컬럼을 참조하는데 로컬 DB엔 없음). `literacy_admin.py`/`base.html`/`literacy` 템플릿 어디서도 `pipeline_jobs`를 참조하지 않고, `git status`상 `suneung.py`/`app/models/*.py`/`app/database.py`는 전혀 수정되지 않아 이번 작업이 원인이 아님을 확인했다. 로컬 개발 DB의 사전 존재 문제로 보고만 남긴다(고치지 않음).
9. **로그인 전후**: 로그인 전 `/literacy/health` 302, 로그인 후 200 확인.
10. **`git status`**: 의도한 파일만 변경 - `app/literacy/models.py`, `app/routers/literacy_admin.py`, `app/templates/base.html`(수정), `app/literacy/migrations/003_review_fields.py`, `app/templates/literacy/*.html`(5개), `docs/literacy/06-검수UI.md`, `06-검수UI-결과.md`(신규).
