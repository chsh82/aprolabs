# Phase 2 — 속담·관용구 수집 파이프라인 (완료, 실제 구현 기준 개정)

> 이 문서는 최초 설계(API 순회 방식)로 작성됐으나, 실측 결과 그 방식이 동작하지
> 않는 것을 확인하고 **전체 덤프 다운로드 + XML 파싱 방식으로 전면 교체**했다.
> 아래 내용은 실제 구현·검증을 마친 최종 상태다. API 순회 방식이 왜 안
> 됐는지는 6절에 남겨서, 나중에 같은 시도를 반복하지 않도록 한다.

## 0. 시작 전에

`docs/literacy/00-현황.md`와 `docs/literacy/01-스키마.md`를 먼저 읽어라.
작업 브랜치는 `literacy-db`다. 다른 브랜치면 전환한다.

---

## 1. 목적

한국어기초사전(krdict)에서 **속담·관용구를 수집해 `terms`(+ 다의어는 `examples`) 테이블에 저장하는 배치 스크립트**를 만든다.

이 단계의 진짜 목적은 속담 데이터 자체가 아니라 **파이프라인 검증**이었다. 다음 네 가지가 실제로 동작하는지 확인하는 것이 핵심이었고, 전부 확인됐다(9절 참고).

1. 중복 방지(`UNIQUE(source, external_id)`)가 실제로 먹는가 → 먹는다. 단, `external_id` 설계 자체를 한 번 바꿔야 했다(5절).
2. 수집 이력이 `collection_runs`에 남는가 → 남는다.
3. 원본 응답이 `raw/`에 파일로 쌓이는가 → 쌓인다(이번엔 API 응답이 아니라 전체 덤프 zip/xml).
4. 중단·재실행이 안전한가 → 안전하다(재실행 시 신규 0건).

이 네 가지가 검증됐으므로 다음 카테고리(어휘 등)는 같은 틀의 반복이다.

## 2. 절대 금지 사항

- 기존 수능 DB에 어떤 경우에도 쓰기를 하지 않는다
- 기존 라우터·에이전트·모델 파일을 수정하지 않는다
- `app/literacy/models.py`의 스키마를 변경하지 않는다. 필드가 부족해 보이면 **고치지 말고 보고하라**
- 서버(`34.158.219.100`)에 접속하지 않는다
- 절대경로 하드코딩 금지. `Path(__file__).resolve().parent` 기준 상대경로만 사용한다
- **API 키를 코드에 직접 쓰지 않는다.** (결과적으로 이 단계는 API를 쓰지 않게 됐지만, 원칙은 유지)
- 검수 UI, 퀴즈 생성 코드를 만들지 않는다

---

## 3. DB 접근 방식

**ORM을 쓰지 않고 raw `sqlite3`로 작성했다.** 기존 프로젝트의 독립 배치 스크립트 패턴을 그대로 따른다.

이유: 수집(덤프 다운로드 + 파싱)은 시간이 걸리고 실패 지점이 여러 곳이라, 웹앱 세션에 묶이면 안 된다. `app/literacy/db.py`의 `get_db_path()`로 DB 경로만 가져와 직접 연결한다. 연결 시 `PRAGMA foreign_keys=ON`을 켠다.

## 4. 파일 배치 (실제)

```
scripts/literacy/
├── __init__.py
├── krdict_dump.py        # 덤프 다운로드 + 캐시 + XML 파싱 (재사용 대상)
```

**최초 계획과의 차이**: `krdict_client.py`(API 클라이언트)로 계획했으나, API 방식을 버리면서 "클라이언트"가 아니라 "덤프 다운로드+파서"가 됐다. 그래서 이름을 `krdict_dump.py`로 바꿨다. `krdict_dump.py`는 Phase 3(어휘) 수집에서도 그대로 재사용한다 — `iter_entries()`가 `lexicalUnit` 값과 무관하게 전체 엔트리를 순회하므로, 호출부에서 필터링할 카테고리만 바꾸면 된다.

## 5. 실제 데이터 소스 — krdict 전체 내려받기

### 5.1 다운로드

- URL: `https://krdict.korean.go.kr/dicBatchDownload?seq=213` (XML 전체 내려받기, seq=212는 Excel, 214는 Json)
- **로그인/인증 불필요** — GET 요청 하나로 즉시 받아짐(브라우저 다운로드 버튼의 실제 요청을 그대로 재현)
- 응답은 ZIP 파일(약 63MB), 압축 해제하면 XML 11개(각 5,000건씩 나뉨, 마지막 파일만 나머지), 전체 56,555개 `LexicalEntry`
- `krdict_dump.py`는 `raw/krdict/krdict_dump.zip`이 이미 있으면 재다운로드하지 않는다(`--redownload`로 강제 가능)

### 5.2 XML 구조 (LMF, `DTD_LMF_REV_16.dtd`)

API 응답(JSON 유사 flat item)과 **완전히 다른 스키마**다. 예시(속담):

```xml
<LexicalEntry att="id" val="16391">
    <Lemma>
        <feat att="writtenForm" val="가난이 죄다" />
    </Lemma>
    <feat att="lexicalUnit" val="속담" />
    <Sense att="id" val="1">
        <feat att="definition" val="가난 때문에 사람이 범죄를 저지르거나 불행을 겪게 된다." />
        <SenseExample>...</SenseExample>
        <Equivalent>...(외국어 대응, 안 씀)...</Equivalent>
    </Sense>
</LexicalEntry>
```

- **속담/관용구를 식별하는 필드**: `<feat att="lexicalUnit" val="..." />`. 값은 `단어`/`구`/`문법‧표현`/`관용구`/`속담` 5가지. 이 필드 하나로 카테고리를 완전히 구분할 수 있다.
- `<LexicalEntry>`는 전부 `<Lexicon>` 바로 아래 같은 레벨의 형제 요소다. **중첩(nesting)이 아니다** — 처음엔 "부표제어는 표제어 안에 XML로 nested되어 있을 것"이라 가정했는데, 실제로는 독립된 `<LexicalEntry>`다(단, ID는 공유한다 — 5.4절).
- 관용구는 `Sense` 안에 `syntacticPattern`(구문 패턴) 필드가 추가로 있을 수 있다. **이번 단계에서는 저장하지 않는다** — 원본이 `raw/`에 남아 있으니 필요해지면 재처리하면 된다.

### 5.3 `terms` 저장값

| 필드 | 값 |
|---|---|
| `category` | `속담` 또는 `관용구` (`lexicalUnit` 값 그대로) |
| `headword` | `Lemma/feat[writtenForm]` |
| `definition` | 첫 번째 `Sense`의 `feat[definition]` |
| `source` | `krdict` |
| `license` | `공공누리 제1유형(출처표시)` |
| `external_id` | 5.4절 참고 — `LexicalEntry@id` 그대로 쓰면 안 됨 |
| `collected_at` | 현재 시각 |
| `review_status` | `검수전` |
| `grade_source` | `auto` |

`grade_level`은 채우지 않는다(NULL). 두 번째 이후 `Sense`(다의어)는 버리지 않고 `examples`에 저장한다: `sentence`=해당 Sense의 definition, `source`=`krdict-sense-{순번}`(2부터).

### 5.4 함정 — `LexicalEntry@id`는 고유하지 않다

**가장 중요한 실측 발견.** 처음 `external_id = LexicalEntry@id`로 저장했더니 `terms`가 2,884건이 아니라 **1,160건만** 들어갔다(원인 분석은 6.3절). 확인해보니:

> `<LexicalEntry att="id">`는 속담/관용구 자신의 고유 ID가 아니라, **그것이 딸려 있는 원 표제어(부모 단어)의 ID를 그대로 물려받은 값**이다.

예: id=`46814`는 원래 표제어 "코"(명사)의 ID인데, "코"와 관련된 관용구·속담 16개("코 먹은 소리", "코가 높다", "코를 골다" 등등)가 **전부 같은 id=46814**를 가진다.

따라서 **`(LexicalEntry@id, headword)` 조합을 `external_id`로 쓴다**: `f"{id}:{headword}"`. 전체 덤프(2,884건)에서 이 조합이 완전히 유일함을 직접 확인했다 — `id` 단독으로는 1,160가지뿐이고, `headword` 단독도 1건 중복("그 나물에 그 밥"이 서로 다른 부모 표제어 아래 두 번 등장)이 있어 둘 다 그냥은 못 쓴다.

### 5.5 덤프 자체의 결함 — 0x08 제어문자

11개 XML 파일 중 4개가 `xml.etree.ElementTree`의 엄격한 파싱에서 `not well-formed (invalid token)` 에러로 실패했다. 원인은 XML 1.0 규격상 금지된 **`0x08`(백스페이스) 제어문자**가 문자열 안에 그대로 섞여 있었던 것 — 정부 제공 덤프 자체의 데이터 결함이다.

실제 위치를 전부 확인한 결과 7건 모두 `<Equivalent>`(외국어 번역, 아랍어 등) 안의 `feat[definition]`/`feat[lemma]`였고, **우리가 읽는 필드(`Lemma`/`lexicalUnit`/`Sense[definition]`)에는 한 번도 나타나지 않았다.** 그래서 파싱 전에 정규식(`[\x00-\x08\x0b\x0c\x0e-\x1f]`)으로 제어문자를 제거하고 `ET.fromstring()`으로 파싱한다 — 우리가 쓰는 데이터에는 영향이 없다.

## 6. 실패한 시도 — API 순회 방식 (참고용, 재시도 금지)

최초 계획은 검색 API(`https://krdict.korean.go.kr/api/search`)를 `part=ip`(관용구·속담), 한글 자모 14개 시드로 순회하는 방식이었다. **실측 결과 이 방식은 근본적으로 동작하지 않는다.**

### 6.1 `target` 파라미터를 잘못 이해했음

당초 `target=9`를 "속담 카테고리 필터"로 가정했으나, 실제로는 **"검색어를 어느 필드에 매칭할지"**를 뜻하는 파라미터다(1=표제어, 2=뜻풀이, …, 8=관용구, 9=속담 — 즉 "속담 필드로 검색해라"라는 뜻이지 "속담만 걸러라"가 아님). 진짜 카테고리 필터는 `part=ip` 하나다. (오픈소스 파이썬 래퍼 `omarkmu/krdict.py`의 파라미터 매핑 소스로 대조 확인)

### 6.2 `advanced=y` + 비-WORD 타입은 응답이 빈다

`part=ip&advanced=y&target=9`로 요청하면 `total`은 정상 나오지만(예: 114) `<item>` 안의 모든 필드가 완전히 비어 있다(raw byte까지 확인 — 파싱 실수 아님). 위 라이브러리도 "advanced 검색에서 WORD 이외의 search_type은 지원 안 됨"이라고 명시적으로 경고하고 있어 독립적으로 같은 결론에 도달했다.

### 6.3 (advanced 없이) `part=ip`는 한 글자 검색어에 0건을 반환한다

`part=ip` 단독(advanced 없이) + `method=include`는 필드가 정상적으로 채워진 결과를 준다 — 하지만 **한 글자 검색어(가/나/다/…)는 전부 `total=0`**이다. 2글자 이상이어도 실제 부분 문자열이 있어야만 매칭되므로(`나다`→49건, `가나`→0건), "몇 글자 시드면 충분한가"를 증명할 방법이 없다 — 커버리지를 증명 못 하는 수집은 불완전한 DB를 완성된 것처럼 보이게 만드는 위험이 있다고 판단해 이 방식을 폐기했다.

**결론: 검색 API로 속담·관용구를 완전 수집하는 건 이 API 설계상 불가능하다.** 나중에 같은 방식을 다시 시도하지 말 것 — 5절의 전체 덤프 방식을 쓴다.

## 7. 실행 순서 (실제)

1. `--dry-run`으로 파싱 결과 개수 확인
2. 전체 저장 실행
3. **같은 스크립트를 한 번 더 실행** — 행 수가 늘지 않는지 확인(핵심 검증)
4. 최초 실행에서 `terms`가 2,884건이 아니라 1,160건만 들어가는 문제가 실제로 발생 → 원인 분석(5.4절) → `external_id` 조합 수정 → 데이터 삭제 후 재수집 → 정정 확인

(당초 계획에 있던 "시드 1개로 10건만 가져와서 승인받고 멈추기" 단계는 API 순회 방식 자체가 폐기되면서 의미가 없어졌다. 대신 `--dry-run`으로 전체 파싱 결과를 먼저 보여주고 진행했다.)

## 8. 스크립트 요구사항 (실제)

### 8-1. 원본 보관

덤프 zip과 압축 해제된 XML을 `raw/krdict/`에 그대로 둔다. 파싱 로직을 나중에 고쳐도 재다운로드 없이 재처리할 수 있다. `download_dump()`는 이미 zip이 있으면 재사용(재다운로드 안 함), `--redownload`로 강제 가능.

### 8-2. 저장값

5.3절 그대로.

### 8-3. 중복 처리

`INSERT OR IGNORE`로 `UNIQUE(source, external_id)` 위반 시 조용히 건너뛴다. `examples`는 유니크 제약이 없어서, INSERT 전에 `(term_id, source)` 존재 여부를 직접 조회해서 막는다. **재실행해도 행 수가 늘어나지 않는다** — 실측 확인(신규 0건/0건).

### 8-4. 수집 이력

실행 시작 시 `collection_runs`에 `source='krdict-dump'`, `status='running'`으로 행을 만들고, 종료 시(성공/실패 모두) `finished_at`/`status`/`fetched_count`/`inserted_count`를 갱신한다. try/except/finally로 예외가 나도 반드시 마감되게 한다.

### 8-5. 호출 예절

API 순회를 버렸으므로 페이지당 딜레이/재시도 로직은 필요 없어졌다. 덤프 다운로드는 1회성 GET 요청 하나뿐이다.

### 8-6. CLI (실제)

```bash
python scripts/literacy/collect_proverbs.py               # 전체 수집
python scripts/literacy/collect_proverbs.py --dry-run      # DB 저장 없이 개수만 출력
python scripts/literacy/collect_proverbs.py --redownload   # 캐시된 덤프 무시하고 새로 받음
```

(`--seed`, `--limit`은 API 순회 방식 전용이었어서 없어졌다.)
